When an incoming booking for a List cannot become a Booking, for example because it has [no NHI](US-11.1.4), the Scheduling Engine shows a stub in its place on that List. The List's other Bookings are added as usual.

The stub is held on an identifier other than the NHI.

This is so a List with a booking that could not be posted never looks complete, and an incoming booking is never simply refused: "you can't just not accept something, you've got to do something with it, especially if it's a hospital feed" (Greg).

## Acceptance criteria

- **Stub shown.** Given an incoming booking for a List cannot become a Booking (for example it has no NHI), when it is received, then a stub shows in its place on that List.
- **Not keyed on the NHI.** Given a stub, then it is held on an identifier other than the NHI.

## Technical discussion

How a stub sits against the rule that a Booking cannot be saved without an NHI is open: a stub may be a separate record on the List, not a Booking, so the NHI rule still holds for every Booking. Greg: the record "will have an underlying identifier other than the NHI".

## Notes

Greg, 28 October: "We add the list, we indeed add the bookings in the list, but we can't add the booking that hasn't got the NHI, so we stick it in an error queue... maybe we should put a placeholder in the list"; "the reason we need a stub is because you can't post the record because it doesn't have an NHI." Donald: unresolved rows leave "a whole bunch of partial lists... this is where the stubs become even more important."

This sits against the 19 October ruling (OQ-49) that an incoming booking with no NHI waits at intake, on the matching screen only. It stays open until OQ-118, raised for Vanessa and Ben on 28 October, is answered.
