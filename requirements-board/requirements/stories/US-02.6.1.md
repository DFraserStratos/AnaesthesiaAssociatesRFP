When an incoming booking for a List cannot become a Booking, for example because it has [no NHI](US-11.1.4), the Scheduling Engine shows a stub in its place on that List. The List's other Bookings are added as usual.

The stub is held on an identifier other than the NHI.

This is so a List with a booking that could not be posted never looks complete, and an incoming booking is never simply refused.

## Acceptance criteria

- **Stub shown.** Given an incoming booking for a List cannot become a Booking (for example it has [no NHI](US-11.1.4)), when it is received, then a stub shows in its place on that List.
- **Not keyed on the NHI.** Given a stub, then it is held on an identifier other than the NHI.

## Technical discussion

A stub is not a Booking, so the rule that [a Booking cannot be saved without an NHI](US-11.1.4) still holds for every Booking (OQ-118). Greg: the record "will have an underlying identifier other than the NHI".

## Notes

Donald: unresolved rows leave "a whole bunch of partial lists... this is where the stubs become even more important."
