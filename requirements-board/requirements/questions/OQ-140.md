Each Procedure now holds its own payer, filled in from the patient, so two Procedures on one Booking can bill two different people. When the payer on one Procedure is changed, the system offers the same change on the Booking's other Procedures that bill the same payer, ticked by default.

1. **Do two Procedures on one Booking ever need different payers?** For example, a parent paying for one procedure and a family trust for another, or a cosmetic procedure paid by someone other than whoever pays for the main one.
2. **Is offering the change to the other Procedures right?** Or should one change always apply to every Procedure on the Booking billed to that payer?
3. **Does the payer follow the Procedure, as an event does?** Greg said an event "is attached to the procedure, not to the booking... So therefore it should use the procedure's details", while on 28 October he agreed one payer per Booking. Does the same reasoning carry to the payer, so each Procedure bills its own?

What hangs on the answer: whether the [payer](US-11.2.2) stays on each Procedure or goes back to one per Booking, and with it how invoices and [prepayment invoices](US-06.3.1) group by payer and whether a [split](US-08.2.3) can name another person.

Recommendation: keep a payer on each Procedure, with the change offered to the others. It matches the technical design v6, which held the patient's and an alternate payer's contact details on each booking procedure, and costs nothing when every Procedure has the same payer.

**Background:**

- v6 design, 16 October: patient_contact_details ("Also the default billable party"), payer_contact_details and alternate_payer on BOOKING_PROCEDURE. See "Notes 2026-10-16 · Pricing model documents v6 #29"
- 28 October: the catalogue read the payer as one per Booking ("Every booking names a payer... I think that's right, it's pretty simple"), with a "different payer" tick (Greg). See "Notes 2026-10-28 · AA meeting with Greg #29 #30 #33"
- 28 October, same meeting, pointing the other way: Greg said an event "is attached to the procedure, not to the booking... So therefore it should use the procedure's details." See "Notes 2026-10-28 · AA meeting with Greg #31"
- Donald, 17 November, chose a payer on each Procedure for the build, to keep the system open and flexible, with a later Procedure copying the payer and invoices and prepayment invoices grouped by payer. See "Notes 2026-11-17 · Donald payer per procedure #1 #2 #3 #4 #5 #11"

## Answer

Donald, 18 November 2026, taking the recommendation: keep a payer on each Procedure, with a change to one offered to the others.

1. **Yes, two Procedures on one Booking can need different payers.** Each Procedure holds its own payer, filled in from the patient, so a parent can pay for one procedure and a family trust for another. Where every Procedure has the same payer, nothing changes for the user.
2. **Offering the change is right.** When one Procedure's payer is changed, the system offers the same change on the Booking's other Procedures that bill the same payer, each ticked by default; the user can untick any and is never made to apply it.
3. **Yes, the payer follows the Procedure, as an event does.** This matches Greg's technical design v6, which held the payer's contact details on each booking procedure, and his point that an event uses the procedure's details.

Invoices and prepayment invoices group by payer, and a split can name another person, as in "Notes 2026-11-17 · Donald payer per procedure #4 #5 #6".
