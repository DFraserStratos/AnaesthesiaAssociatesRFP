The catalogue has an RVG code master (US-05.1.1) and a procedure master (since retired). On 2026-10-02 Donald said the system holds no RVG guide, only "an RVG master list, or... a procedure master... a list of procedures that has RVG-code references within it", and Greg agreed to call it the procedure master. The unique, human readable system code was added on the board to the RVG code master, but the line Donald described as needing it is a procedure on his list (a brow lift that shares an RVG code with other procedures).

1. Are the RVG code master and the procedure master one list, or two (the RVG codes as reference, and the procedures that reference them)?
2. Which carries the unique system code: each procedure, each RVG code, or both?
3. Do procedures sit under RVG codes as children (Greg), or as a flat list each with an assigned RVG code (Donald)? Greg: "we'll find that we come back to a navigation discussion."

Recommendation: one procedure master, each line with its own system code and an RVG code reference; keep RVG codes as reference data only.

Update 2026-10-07: moved, not settled.

- One managed list between the booking text and the RVG is agreed, called "procedure". Greg: an "intermediate level... next level down from the RVG" that "encapsulates a whole family"; "We'll call it a procedure." Donald: AA decides how fine it is, with RVG codes attached, as a way "to more easily discover and pick the contracts that are relevant". Greg later: the standard procedures "have a one to one relationship with the RVG".
- Size: Greg expected "a couple of 1000"; Donald's working list, pared from about 2,000 Solutions Plus rows, is about 400, each row to get an RVG code and base units, and Vanessa and Ben are filling it in.
- Questions 1 and 3: the guide (taken as true for now) and the draft technical design have two levels, RVG groups as published and procedures each belonging to exactly one group ("No nesting of procedures"), with the office finding a procedure by body area, then subgroup, then procedure. Greg and Donald left hierarchy against flat list unsettled on 7 October.
- Question 2: not answered. The draft design gives RVG groups a surrogate key, because "RVG codes are not unique enough to be keys".

## Answer

One list: the RVG groups. The procedure master goes.

- Donald, 14 October: "we're not linking contracts to procedures anymore. We're linking them directly to RVG codes." The intermediate "medium list... That's out the window": on a Booking the office or anaesthetist sees the surgeon's plain text, with the RVG code and the Contract to decide. See Notes 2026-10-14 · AA meeting with Greg #1.
- 16 October: "procedures has been neutered to the point where it's actually just a free text field" on the Booking; there is no "capital P procedure" any more (Greg: "Yep"). See Notes 2026-10-16 · AA meeting with Greg #21 #35.
- The v6 technical design drops the PROCEDURE table, the body section field and the body section, group, procedure picker. The only master list is the RVG groups (code, anatomy, procedure wording, base units, modifier units). See Notes 2026-10-16 · Pricing model documents v6 #1 #12 #23.

Question 1: one list, the RVG groups, held as reference data. Question 3 falls away: there are no procedures to nest. Question 2: an RVG group keeps a hidden key (RVG codes are not unique enough to be keys) plus its published code; Contract lines carry their own system line key and the holder's optional reference code (Notes 2026-10-16 · Pricing model documents v6 #44). Whether RVG groups also carry the human readable system code Greg asked for on 2 October is not restated; it stays on [RVG groups](US-05.1.1) for now.

The v6 documents also propose routine procedures as lines on No contract (RVG); Greg relayed on 14 October that Nick and Ben had dismissed a list of favourite procedures, and Donald wants to build without an intermediate list. That is a separate new question.
