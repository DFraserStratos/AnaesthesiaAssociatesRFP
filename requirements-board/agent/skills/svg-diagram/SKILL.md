# Explainer diagrams (SVG)

Hand-built SVGs, generated by a small Python script, rendered to PNG with Playwright and checked by
eye, then saved as **catalogue artifacts**: the SVG beside a sidecar that names it and marks its
regions, so requirements can link to the diagram or to a spot in it (the Requirements Board's
Artifacts tab shows them, the spot in a red box). The reference diagrams for the style are listed
under "This repo"; `examples/the-requirements-loop.py` is the kit's own, a project-neutral example
(the starter catalogue's loop diagram): six numbered step cards in a ring round a charcoal hero
panel, chevrons between them, dashed side-input cards, a bracketed note and a summary bar; its
sidecar's `steps` make it the kit's stepped example too. The artifact format is under Artifact file
in `REQ/SCHEMA.md`.

## Files in this skill

- `svgkit.py`: palette, primitives and components (`Diagram`, `panel`, `heading`, `tree_section`,
  `tree_collapsed`, `tree_trunk`, `stacked_group`, `table_header`, `table_row`, `step`, `card`,
  `chevron`, `down_arrow`, `pill`, `aside`, `bottom_bar`; `note` is the legacy yellow callout).
  Start new diagrams from this. `rect`, `panel`, `card`, `stacked_group`, `step`, `aside` and `note`
  take an optional `id=`: give every part a
  requirement might point at one (`id="stage-3"`), so its region's anchor is `#stage-3`. That `id`
  lands on the part's rectangle alone; to name a part with its texts (and what a step reveals),
  draw it inside `with d.group(id="stage-3"):` (or `cls=` for a class; groups nest).
- `render.mjs`: SVG to PNG at the SVG's own size. `node BOARD/agent/skills/svg-diagram/render.mjs <in.svg> [out.png]`
- The board's `artifact:steps` script: screenshots a stepped diagram in the running board, the
  whole drawing and then each step (see Stepped diagrams).
- `examples/`: the generators of the reference diagrams. `the-requirements-loop.py` imports
  `svgkit`; older ones may carry their own copies of the helpers. Read them for layout patterns,
  coordinates and copy, and keep them runnable (`python3 examples/<name>.py <out.svg>`).

## Workflow

1. **Decide the audience and the one question the diagram answers.** A user-facing view (what
   people see and choose) and a system view (how it works behind the screens) are different
   diagrams with different layouts; never mix them in one image, and never give two diagrams the
   same layout if they explain different things.
2. **Gather real content first.** Use real names, codes and figures from the repo (catalogue,
   its source documents in `REQ/artifacts/files/`, other data files) where they exist. Invented figures are
   fine for illustration; keep them plausible and consistent across rows.
   **Recreating a supplied image:** keep its content and structure as drawn, but fix terms and copy
   to match the catalogue and `domain-model.md` (a stale name, a typo, a hierarchy the model has
   since settled). Add nothing the image doesn't have (no extra notes, pills or panels) unless the
   user agrees first. Report every change you made to their content.
3. **Write a generator script** in the scratchpad (not the repo) that imports the kit:
   ```python
   import sys; sys.path.insert(0, "<repo>/BOARD/agent/skills/svg-diagram")
   from svgkit import *
   d = Diagram(W, H, title="Short name")
   ...
   d.save(sys.argv[1])
   ```
   Lay out with explicit coordinates and keep layout numbers as named constants (column x
   positions, row pitch) so later edits are one-line changes. Derive the canvas width from the
   content widths (`W = HX + HW + 20`), not the other way round, so tightening a column shrinks
   the whole image.
4. **Render and look**: `node BOARD/agent/skills/svg-diagram/render.mjs out.svg`, then Read the PNG.
   SVG cannot measure text, so the PNG is the only proof that nothing overlaps or overflows. Fix,
   re-render, repeat until the checklist below passes.
5. **Save it as an artifact** (unless the user wants it somewhere else):
   `npm --prefix BOARD run artifact:new -- <scratch>/out.svg --title "<what it explains>" --kind diagram --date <today> --author "..." --source "..."`.
   It takes the next `AR-nn`, copies the SVG to `REQ/artifacts/files/AR-nn.svg` and writes the
   sidecar. The PNG stays in the scratchpad: it is only the check render (the board draws the SVG,
   sharp at any zoom). Revising an existing diagram: overwrite its `artifacts/files/AR-nn.svg` in place, keep its ID.
6. **Mark its regions** in the sidecar, one per part a requirement might point at (each stage,
   panel, group, note): `around: ["#stage-3"]` where you gave the part an `id`, else
   `text=<its exact heading text>` or a `rect[x="..."][y="..."]` selector; the box goes round
   every anchor's match together. Add a one-line description of the diagram. A stepped diagram
   gets its `steps` here too (Stepped diagrams, below).
7. **Link requirements** to it, unless the user has named the items. Hand the search to a
   **Sonnet subagent** (Agent tool, `model: "sonnet"`) once the sidecar is written. Give it the
   artifact ID, the sidecar path and its region IDs, and tell it to:
   - search `REQ/stories/` for the items the diagram illustrates;
   - read each item in full before linking it, never link on a keyword match alone;
   - pick the most specific item per region (story over feature over epic), and link the epic to
     the whole diagram (`AR-nn`, no region);
   - add the link as a block list just before `images:` in the item's frontmatter (`artifacts:`
     on its own line, then `  - AR-nn#region`, one link per line), or append a line to an existing
     `artifacts:` list; never the inline `[...]` form, which the board rewrites, so the file fails
     its round-trip test;
   - report each link with a one-line reason, and not run the check (agent shells often have a
     Node too old for the board's `.ts` scripts).

   Then **review its links yourself**: drop any that only share a word with the diagram, and add
   any obvious one it missed. Run the check ("This repo"; it fails when an anchor matches nothing,
   and with `ERR_UNKNOWN_FILE_EXTENSION ".ts"` when the Node on `PATH` is too old). Report briefly: the artifact, the links, and anything you
   corrected or left out.

## Stepped diagrams

A stepped diagram is an ordinary SVG artifact whose sidecar lists `steps` (Steps, under Artifact
file in `REQ/SCHEMA.md`). The board plays them one at a time: each step reveals more of the
drawing, highlights what the step is about, and shows a caption and a small balances table beside
it. A requirement can link to a step as it can to a region (`AR-nn#step-id`).

**When it earns its place.** A flow that unfolds, where the reader needs to see what changed at
each stage: an order moving through its states, entries building up in a ledger, money moving
between accounts until they net to zero. When the reader needs the whole structure at a glance (a
model, a hierarchy, a set of choices side by side), or the stages don't build on each other, a
static diagram is better. Numbered parts alone are no reason to step a picture.

1. **Draw the finished picture first**, as an ordinary diagram that passes the spacing checklist
   with everything visible. It is what the thumbnail, the minimap and comparisons show, and what
   the board shows when no step is chosen, so it has to read on its own.
2. **Reveal is cumulative, and nothing is hidden again**: a step shows everything the steps up to
   it reveal. So lay each step's marks out in space (ledger entries accumulating down an account,
   cards in a row, a list that grows), never one mark replacing another in the same place. A value
   that changes from step to step belongs in `balances`, not drawn twice on top of itself.
3. **Wrap each step's marks in a group with an id**, so one anchor reveals the whole of them:
   ```python
   with d.group(id="s2-shipment"):
       d.card(x, y, w, h, title="Shipment", number=2)
       d.lines(x + 18, y + 76, ["Two boxes leave the warehouse."], fill=MUTED)
   ```
   Use `cls=` when one step reveals marks in several places (`.s2`, anchored as `.s2`). Anything no
   step names stays visible throughout: the frame, the headings, the standing accounts.
4. **Write `steps` in the sidecar**, after `regions`, in block style, one anchor per line (the board
   rewrites a flow-style `[...]` list on its next save). Quote an anchor that starts with `#`, and
   any amount YAML would read as a number (`"0"`).
   ```yaml
   steps:
     - id: order-placed
       name: Order placed
       group: One order
       caption: The customer orders two boxes. Nothing has left the warehouse yet.
       show:
         - "#s1-order"
       highlight:
         - "#s1-order"
       balances:
         - account: Ordered
           amount: "2"
         - account: Shipped
           amount: "0"
     - id: boxes-shipped
       name: Boxes shipped
       group: One order
       caption: The warehouse ships both boxes, and the order is complete.
       show:
         - "#s2-shipment"
       highlight:
         - "#s2-shipment"
         - "#warehouse"
       balances:
         - account: Ordered
           amount: "2"
         - account: Shipped
           amount: "2"
   ```
   - `id`: lower-case words joined by hyphens, named for what happens (`boxes-shipped`, not
     `step-2`), so a step put in later breaks no link. Never a region's id: steps and regions share
     one set of spots.
   - `name`: a few words, shown in the step list. `group`: optional; consecutive steps with the same
     label sit under one heading (one worked example each).
   - `caption`: one or two plain sentences, what happened at this step and what it means. Links
     and record IDs work.
   - `show`: the groups this step reveals.
   - `highlight`: what the step is about, usually what it just revealed plus any standing part it
     changed (the account the money went to). The rest dims. Leave it out where nothing should dim,
     and never highlight what a later step reveals (the check warns: it is still hidden).
   - `moves`: optional, what travels at this step (below).
   - `balances`: running totals that change, as plain-text rows. The board draws them beside the
     caption and marks the rows that changed, so they need not be in the picture. Keep the same rows
     in the same order on every step.
5. **Moves, for what genuinely travels.** When a step carries something from one place to another
   (an amount leaving one account for another, a document sent from one system to the next, an
   item shipped from a store to a customer), list it under the step's `moves`, and the board flies
   it there as the reader steps forward onto the step:
   ```yaml
       moves:
         - from: "#store-box"      # where it sets off: visible at this step
           to: "#customer-box"     # what travels and where it lands: revealed by this step
   ```
   Draw both ends as real marks: the origin is already in the picture (the entry it leaves, the
   account it comes from), and the destination is a mark of its own, revealed by this step. Give
   the travelling mark its own id (a group holding the card or entry that arrives), not a whole
   panel, so only it flies. `from` uses its first match, and every match of `to` flies from it;
   several moves on one step fly in order, a moment apart. Use moves sparingly: one or two per step,
   only for what really changes place. Something that merely appears, or a total that changes, is a
   reveal or a balance, not a move. Jumping to a step, stepping back and reduced motion show the
   step without the flight, so the finished picture must explain itself without it.
6. **Choose the view: `fixed` or `follow`.** A diagram that fits on one screen stays `fixed` (the
   default: leave `step_view` out), so the view never moves as it steps. A wide flow that does not
   fit one screen (a long left-to-right strip) sets `step_view: follow` in the sidecar, beside
   `steps`: the board then frames each step's focus as the reader arrives, when it is not already in
   view. The focus is what the step highlights (else what it reveals) plus both ends of its moves,
   so keep each step's highlight compact, and its moves short: the view frames all of it, and a
   focus spread across the strip can only be framed small.
7. **Regions still work**, and should mark the standing parts (each account, panel or ledger), so a
   requirement can point at them whatever step is showing.
8. **Check every step by eye.** With the board running ("This repo"),
   `npm --prefix BOARD run artifact:steps -- AR-nn [--out <dir>]` writes `00-whole.png`, then
   `01-<step-id>.png`, `02-<step-id>.png` and so on, at a laptop size (its out folder is printed at
   the end). It shoots the board of the worktree it runs in (`BOARD_PORT`, as the dev server takes it;
   `--url <base>` names another), so start that board first. Read every one: the right things visible and highlighted at each step, nothing
   appearing before its time, no caption that disagrees with the picture. Step forward through the
   moves in the board too: each mark should set off from its origin and land without a jump. Then
   run the check: it errors on a `show`, `highlight` or move anchor that matches nothing, a move
   missing `from` or `to`, and a step id that clashes, and warns on a highlight not yet revealed, a
   move's `from` or `to` not yet revealed, and a `from` that matches several marks.

## Visual language

**Canvas.** Page background `#F3F6FA`. No title text on the image: content starts 20px from the
top, with the same 20px outer margin on every side (use `top_crop` or simply start at y=20). Size
the canvas to the content: as compact as it can be without crowding. No wasted space: cards no
wider than their longest line plus padding, arrow gaps just wide enough for their labels, side
columns no wider than their notes need (rewrap a note rather than widen its column). Only widen
when the spacing checklist fails.

**Type.** Font stack `'Schibsted Grotesk', 'Helvetica Neue', Helvetica, Arial, sans-serif`.
Panel headings 27 to 29 / 800. Card and group titles 18 to 21 / 700 to 800. Body 15 (row names),
12.5 to 14 (captions, muted `#55555E`). Pills 11 to 12.5 / 600. Bottom bar 19, labels 800.

**Shape.** Rounded rectangles everywhere: panels r12 to 14, cards and groups r9 to 10, rows r7,
pills fully rounded. Strokes 1.2 to 1.6px. Tree connectors are the one heavy line: `#2E2E31`,
2.2 to 2.5px, rounded caps.

**Colour roles** (constants in `svgkit.py`):

| Role | Fill / stroke | Use |
|---|---|---|
| List panel | `BLUE` / `BLUE_S` | a master list or tree |
| Hero panel | `CHAR` (charcoal), text white / `LIGHT` | the main subject of a user view |
| Side column | `#F1EDFD` / `LAV_S` | steps, "how to" |
| Section box | `GRN` / `GRN_S` | a top-level group inside a list |
| Sub-box | `SUB` / `SUB_S` | a nested group |
| Leaf item | `PEACH` / `PEACH_S` | the specific thing (an order line) |
| Summary bar | `YEL` / `YEL_S` | the bottom bar only (notes are asides, see below) |
| Kinds | `KIND["green" / "lavender" / "rose"]` | one colour per category of thing; never two similar hues for different kinds |
| State pills | `GOOD_F/GOOD_T` yes, `LOCK_F/LOCK_T` no or locked | a yes/no attribute |
| Pricing pills | `UNITS_*` green for units × rate, `CHIP`/`CHIP_T` grey for a fixed price | how a row is priced |
| Payer pills | `PERSON_*` orange (a person, e.g. the customer), `INSURER_*` indigo (a third party), `HOSPITAL_*` teal (an organisation): one colour per payer type | who gets the invoice |
| Highlight | `WIN` green outline | the winning value, the rule that applied |
| Accent | `ACCENT` blue | numbered circles, flow chevrons |

Keep each colour to one meaning within a diagram. When things come in kinds, add a small key
(three swatch cards) near where the kinds first appear.

**Recurring patterns.**

- *Tree*: section boxes ticked off a trunk; the trunk starts above the first tick so the list
  implies a parent off-picture. Expand two or three sections, then collapsed grey rows with a `…`
  row, then the last few. A dashed peach connector can link a leaf to where it is used.
- *Stacked group*: kind-coloured card with an offset shadow (reads as "one of many"), a solid
  stripe on the left, title left, a plain right-aligned note (when it is shown, who it is for) rather
  than another pill, white rows inside, caption below. Keep pills for row values; too many pills
  turn into noise.
- *Table inside cards*: one dark header band with dividers; every row repeats faint dividers at
  the same x positions so columns run straight through all the cards. Badges that classify a row
  ("System generated", "Submitted by supplier") sit right-aligned in the name column.
- *Steps*: numbered white cards; a short value chip on the right for pick-one steps, two or three
  lines of muted text for explain steps.
- *Flow*: equal stage cards left to right with `chevron`s in the gaps, a running example carried
  through every stage, then a full-width worked-examples table.
- *Bottom bar*: one sentence that sums the diagram up, `Label:` bold, parts joined by `·`.
- *Note (aside)*: **every note uses `aside`**: an open square bracket with muted italic text
  beside it, no box and no fill (a "good to know", a caveat, something that may happen). Never a
  yellow box, and never a card in a flow: a note is not a step, so flow lines and chevrons never
  run through it. Hang it off the thing it is about with a dotted leader that goes straight down
  (or across) and turns into the middle of the bracket's side, never its top corner; a free-standing
  note (about the whole panel) has no leader. An optional first line in bold italic titles it.
  The example generators show it (a local `aside` helper in each); AR-01, AR-02, AR-17, AR-21 and
  AR-22 all use it.

**Copy.** Short, plain sentences. Use `·` as a separator and "to" for ranges; avoid en and em
dashes. `→` is fine for sequences. Names over codes, but show the code where users see it
(`Face Lift - H3`).

## Spacing checklist (check on the PNG, every time)

- At least `PAD` (14px) between any box edge and its contents, including pills and value cells
  at the right-hand end of a row.
- No text touching or crossing another box, line or arrow; arrows visible in their own gap.
- Captions clear of the card below; footnotes clear of the panel bottom.
- A note's dotted leader enters the middle of its bracket's side and crosses no text.
- Columns line up from header to last row.
- Pills fit their label (widen the pill, not shrink the text).
- Panels in a row share top and bottom edges; leftover space is spread, not dumped at one end.
- Nothing runs past the canvas; the 20px outer margin holds on all four sides.
