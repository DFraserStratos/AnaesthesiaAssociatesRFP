Which slice of AA do both teams build?

The sprint needs one piece of the Anaesthesia Associates system that two teams can each design, build, test and release in four days. The full system is far too big for that. This page compares six possible pieces so the panel can pick one.

AA in two minutes

Anaesthesia Associates (AA) runs booking and billing for about 85 independent anaesthetists in Christchurch. Every piece of work follows the same path, from a theatre session being scheduled to the anaesthetist being paid. Each option below builds part of this path.

ListOne anaesthetist's theatre session at a hospital on a given day.
BookingOne patient's operation on a List.
ProcedureA piece of work within a Booking. Procedures are what get billed.
ContractAn agreed price arrangement with a hospital, insurer, surgeon or AA. Choosing the right one is the hardest set of rules in the system.
RVG unitsA standard New Zealand scale that turns an anaesthetic into units, and units into a fee.
XeroThe accounting system that holds AA's invoices and payments.

Recommendation

Build option 1, add List approval if there is time, and keep invoicing back for the outside developer.

BuildBooking to price, 68 stories. The day view, entering a Booking, recording Procedures, Contracts and the fee calculation.
If timeList approval, 8 stories. A List moves from active to submitted to authorised.
Hold backInvoicing, 14 stories. The outside developer builds it by following each team's playbook.

Option 1 holds the rules that make AA hard, so it tests whether a team can check code it mostly did not write. Its tests can be worked pricing examples with one right answer, which keeps the panel's scoring on evidence.

If the panel wants to see the whole journey end to end, option 2 is the step up, as long as Contracts are limited to the common cases. Otherwise both teams are likely to spend the sprint inside the pricing rules.
