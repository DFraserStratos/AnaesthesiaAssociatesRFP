## US-15.0.1 · Ease of use · Contradicts

[US-15.0.1](../../../../requirements-board/requirements/stories/US-15.0.1.md) · [board](http://localhost:5180/#/board?item=US-15.0.1) · status Proposed · surfaces: mobile, web, admin, pwa, domain · confidence medium

- **Requirement:** Intuitive for people uncomfortable with modern systems, most of all on daily operational screens; proposed approach is real screens, per-group training, and in-app guidance at point of need. Notes: anaesthetists see none of the Contract complexity today and the new system must not add it.
- **Prototype today:** Large touch targets, bottom sheets, one clear action, shared capture cards, plain empty states, a few native title tooltips (DayGrid, StatusLegend toggles, SlidingSegmentedControl segment titles). No help component, '?' entry, first-run tips or coach marks. The shared capture block (used by mobile and web anaesthetist views) renders a read-only line with a route chip, contract name, insurer, billable party and reference, and fee labels such as 'FIXED CONTRACT PRICE'. Office-only setup is correctly confined to OfficeBillingSetup.
- **Missing or wrong:**
  - WRONG: anaesthetist capture context line shows contract name, billing-route chip, insurer and billable party (BtmCaptureBlock.tsx:111-115, 186-205); the Notes say anaesthetists must not see Contract complexity. Not role-gated, it renders for the anaesthetist actor.
  - WRONG (minor): fee label 'FIXED CONTRACT PRICE' surfaced to the anaesthetist (CardDetailBody.tsx:219).
  - MISSING: no in-context help affordance (InfoTip/popover/'?') on mobile card capture, admin Day view or admin Review.
  - MISSING: no first-run or onboarding hints, and no per-app Help entry.
  - Training and short standalone docs are not representable in the demo (presenter-narrated only).
- **Evidence:** `aa-prototype/src/shared/capture/BtmCaptureBlock.tsx:111`, `aa-prototype/src/shared/capture/BtmCaptureBlock.tsx:115`, `aa-prototype/src/shared/capture/BtmCaptureBlock.tsx:186`, `aa-prototype/src/shared/card/CardDetailBody.tsx:219`, `aa-prototype/src/shared/card/CardDetailBody.tsx:684`, `aa-prototype/src/shared/StatusLegend.tsx:51`, `aa-prototype/src/apps/admin/components/DayGrid.tsx:314`, `searched: tooltip\|InfoTip\|helpHint\|walkthrough\|coachmark\|onboarding\|what's this\|getting started\|first-run\|help in src -> only native title tooltips and demo-panel hints; no help component`
- **Verifier:** corrected from Partial. Re-grepped for help/tooltip/onboarding: reviewer's absence claim holds (also found StatusLegend and segmented-control title tooltips, minor). Opened BtmCaptureBlock and CardDetailBody: the contract name, route chip and 'FIXED CONTRACT PRICE' reach the anaesthetist unconditionally, since the block is shared and only the office billing setup is role-gated. The reviewer noted this only as a 'verify' item. That is implemented behaviour the Notes say must not exist, so by the Contradicts rule I changed Partial to Contradicts. Size M and surfaces kept, with domain added for any role-aware label helper. It is arguably a soft contradiction because the Notes are guidance rather than an acceptance criterion.

## US-15.0.4 · Volumes · Partial

[US-15.0.4](../../../../requirements-board/requirements/stories/US-15.0.4.md) · [board](http://localhost:5180/#/board?item=US-15.0.4) · status Proposed · surfaces: simulator, store, seed, domain, shell, admin, demo-guide · confidence medium

- **Requirement:** Handle about 85 anaesthetists, 20,000 Slot records within the four-month horizon (FT-01.1) and 28,000 invoices a year without any drop in performance.
- **Prototype today:** Seed: 14 anaesthetists across the horizon (~3,900 Lists). canvasRoll.test.ts generates 85 x horizon in a pure function. Xero sim and Master data show narrated volumeStory (28,000 invoices/yr, 9,820 of 10,000 contacts). Admin DayGrid states 'At production scale (~85) this view pages and virtualises; scale is narrated here, not simulated'. Data Inspector shows persisted bytes against a 5 MB budget; Audit viewer caps at 500 rows.
- **Missing or wrong:**
  - No full-scale dataset selectable in the UI (85 anaesthetists, ~20,000 Slots, 28,000 invoices)
  - Admin Day grid, Review queue, Invoices table and Audit not exercised at scale (Audit capped at 500, DayGrid narrates paging); localStorage persistence (5 MB, pauses on quota) cannot hold a full-scale state
  - Invoice history near 28,000 is narrated only, none generated
  - No performance readout (render/query timings) to show 'no drop in performance'
- **Demo trigger:** Button 'Load full-scale data (85 anaesthetists, ~23,000 Lists, 28,000 invoices)' in the Control Panel, and a contextual shortcut in the bar shown only on Admin Day / Invoices: builds the large dataset in memory (persistence paused), shows generation and render timings; Reset returns to normal seed.

## US-15.0.3 · Enter once · Partial

[US-15.0.3](../../../../requirements-board/requirements/stories/US-15.0.3.md) · [board](http://localhost:5180/#/board?item=US-15.0.3) · status Proposed · surfaces: domain, store, admin, web, seed · confidence medium

- **Requirement:** Data entered once stays current everywhere (hospitals, surgeons, statuses, rates by identity); reference data is locked once a Procedure is authorised (US-04.3.5) so an issued invoice can never be rewritten by later changes.
- **Prototype today:** Lists/Cards/Procedures hold hospitalId, surgeonId, anaesthetistId, governingContractId by ID; single zustand store so an edit shows in every app at once. authoriseList triggers a synchronous billing run that writes Invoice/InvoiceLine amounts (rate text snapshotted into line description only). editAnaesthetist unit value and editContract mutate masters live.
- **Missing or wrong:**
  - No snapshot of contract version / RVG values / anaesthetist unit value onto the Procedure at AUTHORISED (Procedure holds only governingContractId; no snapshot fields in domain/types.ts)
  - procedureFee/cardFee read anaesthetist.unitValue, contract and RVG live from masters, so an authorised Card's fee display drifts from the issued invoice after a later master edit
  - Billing-run retry (Resolve and retry) re-reads current masters, so authorised-but-not-yet-billed Lists are not frozen; billingRun.test.ts:454-466 encodes a post-completion unit-value change producing allocationStale failure rather than a locked value
  - No test asserting a post-authorisation master edit leaves invoice or displayed totals unchanged
  - Master data has no hospital rename/edit or surgeon CRUD (only createHospital, holidays, anaesthetist edit, contracts), so 'change once, shows everywhere' cannot be demoed for those entities
  - No UI indication that reference data is locked on an authorised Card/Procedure (US-04.3.5 shows locked billing setup)
- **Demo trigger:** Existing Master data edit (Admin > Master data > Anaesthetists > edit unit value) is the trigger. Beat once built: authorise a List, change Souter's unit value, show invoice and locked Card total unchanged while a new DRAFT Card uses the new rate. Optional: hospital rename in Master data for 'change once, shows everywhere'.
- **Evidence:** `aa-prototype/src/shared/capture/feeContext.ts:30-60 (live masters lookups)`, `aa-prototype/src/domain/billing/fee.ts:187 (ctx.anaesthetist.unitValue)`, `aa-prototype/src/domain/billing/invoiceBuild.ts:243-258 (only rate text in line description)`, `aa-prototype/src/domain/types.ts:454 (governingContractId only) and :662-685 (Invoice/InvoiceLine amounts)`, `aa-prototype/src/store/mastersActions.ts:183 (comment: editAnaesthetist unit value re-prices via live unitValue)`, `aa-prototype/src/store/contractActions.ts:106-150 (editContract mutates in place, no version)`, `aa-prototype/src/store/billingRun.test.ts:454-466`, `searched: snapshot\|frozen\|freeze in src ts -> only comments`

## US-15.0.6 · Privacy and data minimisation · Partial

[US-15.0.6](../../../../requirements-board/requirements/stories/US-15.0.6.md) · [board](http://localhost:5180/#/board?item=US-15.0.6) · status Proposed · surfaces: admin, simulator, store, domain, shell, demo-guide · confidence medium

- **Requirement:** NHI stays in the core platform and never goes to Xero (US-09.3.1); never leaks via logs, errors, monitoring or non-production data; dead-lettered HL7 (full PID) surfaces only what is needed with raw payload restricted; non-production holds synthetic data only.
- **Prototype today:** xeroNhi.test.ts scans the Xero slice after the money chain for seeded NHIs; XeroContact.contactNumber is the hidden id. Admin integration monitor shows time, feed, type, control ID, appointment, patient name, status, failure reason; never NHI or raw message. Only the demo Integration simulator shows raw HL7 with PID (demo surface). 4 console calls, none with patient data; validateNhi reasons and refusal texts do not echo the NHI. Patients fictional; mobile More tab says 'All patients, lists and figures are fictional'.
- **Missing or wrong:**
  - No restricted-access raw-payload concept: a dead-lettered row has no 'view raw message' control gated by role/reason and audited; the Integration simulator shows raw PID freely
  - Message log shows patient name on failed rows; no minimum-needed policy expressed
  - No visible synthetic-data statement in web, admin or harness (only mobile More tab), and no check/scan that logs, messages and Xero stay NHI-free
  - Audit rows patient.create / patient.reuse hold NHI in before/after (intake.ts:118); audit is core platform, but nothing states or tests that audit/telemetry are NHI-free
- **Demo trigger:** (1) Admin > Integrations > Messages, on dead-letter rows: 'View raw message' (office only), asks for a reason, writes audit entry integration.rawViewed, then reveals the PID-masked payload; hidden by default. (2) Data Inspector button 'Scan for NHI leaks' (shown on /demo/data only): searches Xero slice, message log, failure reasons and console-style logs for any seeded NHI and reports zero hits; plus a 'Synthetic data only' badge in the harness bar.
- **Evidence:** `aa-prototype/src/store/xeroNhi.test.ts`, `aa-prototype/src/domain/types.ts:758-767 (XeroContact contactNumber)`, `aa-prototype/src/apps/demo/DemoXero.tsx:58-62 (NHI callout; consistent with OQ-30 Open, so not stale)`, `aa-prototype/src/apps/admin/screens/IntegrationMonitorScreen.tsx:88-118 (columns; patientRef)`, `aa-prototype/src/store/integrationActions.ts:248 (patientRef = name), failureReason texts NHI-free`, `aa-prototype/src/apps/demo/DemoIntegrations.tsx:245-249 (raw HL7 pane)`, `aa-prototype/src/store/intake.ts:114-119 (audit after: { nhi })`, `aa-prototype/src/apps/mobile/screens/MoreScreen.tsx:63-66 (fictional-data statement)`, `console.* in src: pwa/swRegistration.ts:39, pwa/officeSimulation.ts:159, store/persistStorage.ts:111, store/events.ts:29 (no patient data)`
- **Verifier:** corrected from Partial. Verdict Partial upheld. Corrections: (a) dropped the 'stale Xero callout' point, since OQ-30 (NHI in Xero, App.1 vs App.2) is still Open and the catalogue follows App.2 pending AA confirmation, so 'unresolved, needs AA ruling' is accurate; reference OQ-30 (affects US-09.3.1, US-11.1.1).
