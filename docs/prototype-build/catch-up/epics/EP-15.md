## US-15.0.4 · Volumes · Partial

[US-15.0.4](../../../../requirements-board/requirements/stories/US-15.0.4.md) · [board](http://localhost:5180/#/board?item=US-15.0.4) · status Proposed (1) · surfaces: simulator, domain, store, seed, demo-guide · confidence high

- **Requirement:** System handles about 85 anaesthetists, 20,000 Slot records within the configurable scheduling horizon (currently four months) and 28,000 invoices a year without any drop in performance.
- **Prototype today:** Seeds 14 anaesthetists (cast.ts ANAESTHETISTS) with AM and PM Slots over the horizon (appSettings.schedule.horizonMonths, range 1 to 24, settable). volumeStory { invoicesPerYear: 28000, activeContacts: 9820 } is narrated as counters on the Xero simulator and admin masters view, not generated records. listIndexBySlot is memoised 'so a 20,000-Slot grid never scans Lists per cell' but nothing builds or times that scale. Demo Data shows entity counts and storage size only. No performance readout anywhere.
- **Missing or wrong:**
  - No full-scale dataset (85 anaesthetists, about 20,000 Slots, about 28,000 invoices)
  - No timing or performance readout for Day view, availability grid or invoice list at scale
  - Persisted state has a 5 MB budget, so a scale dataset must be in-memory and bypass persistence
- **Demo trigger:** Button 'Load full-scale dataset (85 anaesthetists, 20k Slots, 28k invoices)' on the Demo Data screen (/demo/data): swaps in an in-memory generated dataset (not persisted) and shows load/render timings for the Admin Day view, availability grid and invoice list; 'Back to demo data' restores the seed.

## US-15.0.1 · Ease of use · Partial

[US-15.0.1](../../../../requirements-board/requirements/stories/US-15.0.1.md) · [board](http://localhost:5180/#/board?item=US-15.0.1) · status Proposed (1) · surfaces: mobile, web, admin, pwa, demo-guide · confidence medium

- **Requirement:** System must be intuitive for people not comfortable with modern systems, most of all on daily operational screens. Guidance embedded in the app so help appears at the point of need and standalone docs stay short. Anaesthetist's world stays simple (note: no Contract complexity) and close to the current mobile app.
- **Prototype today:** Anaesthetist mobile is a 4-tab, slide-stack, bottom-sheet design with large controls. BUT the shared BtmCaptureBlock shows every actor (including anaesthetists) a route chip plus a 'Contract · insurer · billable party · reference' context line. No help tips, first-run hints, coach marks or per-screen guidance anywhere in mobile, web or admin; the only coaching is the PWA InstallCoach (Add to Home Screen). More tab is a visual-only persona card with a demo note.
- **Missing or wrong:**
  - No point-of-need or in-context help on mobile capture, Admin Day or Admin Review
  - No first-run hint per app
  - Nothing that reads as embedded guidance keeping standalone docs short
  - Anaesthetist Booking shows a route chip (Hospital / Contract holder / insurer etc.) and Contract/insurer/payer context line (BtmCaptureBlock.tsx:111-206), which sits against the Note 'no Contract complexity'; but Confirmed US-03.1.2/US-03.1.9 now require the Contract on anaesthetist screens, so only the route chip is a likely leftover (plan phase 20/43a handles it)
  - Reviewer's 'FIXED CONTRACT PRICE / FEE @ rate' point is not a live gap: the total panel is not rendered for anaesthetists (BookingDetailBody.tsx:133, 685), it is dead for them today

## US-15.0.3 · Enter once · Partial

[US-15.0.3](../../../../requirements-board/requirements/stories/US-15.0.3.md) · [board](http://localhost:5180/#/board?item=US-15.0.3) · status Proposed (1) · surfaces: domain, store, admin, web, seed · confidence medium

- **Requirement:** Data entered once stays current everywhere (hospitals, surgeons, statuses, rates by identity); reference data is locked once a Procedure is authorised (US-04.3.5) so an issued invoice can never be rewritten by later changes.
- **Prototype today:** Lists/Cards/Procedures hold hospitalId, surgeonId, anaesthetistId, governingContractId by ID; single zustand store so an edit shows in every app at once. authoriseList triggers a synchronous billing run that writes Invoice/InvoiceLine amounts (rate text snapshotted into line description only). editAnaesthetist unit value and editContract mutate masters live.
- **Missing or wrong:**
  - No snapshot of contract version / RVG values / anaesthetist unit value onto the Procedure at AUTHORISED (Procedure holds only governingContractId; no snapshot fields in domain/types.ts)
  - procedureFee/cardFee read anaesthetist.unitValue, contract and RVG live from masters, so an authorised Card's fee display drifts from the issued invoice after a later master edit
  - Billing-run retry (Resolve and retry) re-reads current masters, so authorised-but-not-yet-billed Lists are not frozen; billingRun.test.ts:454-466 encodes a post-completion unit-value change producing allocationStale failure rather than a locked value
  - No test asserting a post-authorisation master edit leaves invoice or displayed totals unchanged
  - Master data has no hospital rename/edit or surgeon CRUD (only createHospital, holidays, anaesthetist edit, contracts), so 'change once, shows everywhere' cannot be demoed for those entities
  - No UI indication that reference data is locked on an authorised Card/Procedure (US-04.3.5 shows locked billing setup)
- **Demo trigger:** Existing Master data edit (Admin > Master data > Anaesthetists > edit unit value) is the trigger. Beat once built: authorise a List, change Souter's unit value, show invoice and locked Card total unchanged while a new DRAFT Card uses the new rate. Optional: hospital rename in Master data for 'change once, shows everywhere'.
- **Evidence:** `aa-prototype/src/shared/capture/feeContext.ts:30-60 (live masters lookups)`, `aa-prototype/src/domain/billing/fee.ts:187 (ctx.anaesthetist.unitValue)`, `aa-prototype/src/domain/billing/invoiceBuild.ts:243-258 (only rate text in line description)`, `aa-prototype/src/domain/types.ts:454 (governingContractId only) and :662-685 (Invoice/InvoiceLine amounts)`, `aa-prototype/src/store/mastersActions.ts:183 (comment: editAnaesthetist unit value re-prices via live unitValue)`, `aa-prototype/src/store/contractActions.ts:106-150 (editContract mutates in place, no version)`, `aa-prototype/src/store/billingRun.test.ts:454-466`, `searched: snapshot\|frozen\|freeze in src ts -> only comments`

## US-15.0.6 · Privacy and data minimisation · Partial

[US-15.0.6](../../../../requirements-board/requirements/stories/US-15.0.6.md) · [board](http://localhost:5180/#/board?item=US-15.0.6) · status Proposed (1) · surfaces: admin, simulator, domain, store, shell, demo-guide · confidence medium

- **Requirement:** NHI stays in clinical and ledger systems and is never sent to Xero or any finance platform in any field. It must not leak via logs, errors, monitoring or non-production environments: failed HL7 messages show office staff only what is needed to resolve the problem, with the raw payload under restricted access; non-prod holds only synthetic data; no client data in AI tools.
- **Prototype today:** Xero contacts and invoice pairs key on the hidden internal ContactNumber; Xero simulator has a 'No personal information in Xero' callout; xeroNhi.test.ts scans the serialised Xero slice for NHI, names, phone, email and address after a full money chain. Admin IntegrationMonitorScreen lists dead-letter rows with patient name, status and a plain failure reason (no NHI, no raw HL7) plus Reprocess; failure reason strings contain no NHI. Console logging is limited to generic text with ids. Seed patients are fictional and the More tab says figures are fictional. The raw HL7 with the full PID segment is shown unrestricted in the /demo/integrations simulator (a demo-only surface).
- **Missing or wrong:**
  - No restricted-access raw-message view in Admin: no role-gated, audited 'View raw payload' action on a dead-letter row
  - No visible synthetic-data / non-production badge or presenter statement of the Dev/Test/UAT rule (only a 'fictional' sentence on the mobile More tab)
  - No NHI leak scan beyond the Xero slice (logs, error messages, audit summaries, monitoring); no-AI-tools rule is process-only and not representable
- **Demo trigger:** Admin Integrations message log: a dead-letter row gets a 'View raw payload' button that asks for a restricted-access confirm, is audited, then shows the PID segment; plus a 'Run NHI leak scan' button on /demo/data that scans error messages, audit summaries, logs and the Xero slice and reports pass/fail.
- **Evidence:** `aa-prototype/src/domain/xeroContact.ts:4-5`, `aa-prototype/src/store/xeroHandoff.ts:8-18,78-82`, `aa-prototype/src/store/xeroNhi.test.ts:1-60`, `aa-prototype/src/apps/demo/DemoXero.tsx:58-59,103`, `aa-prototype/src/apps/admin/screens/IntegrationMonitorScreen.tsx:119-135 (row shows patientRef = patient name, failureReason, Reprocess)`, `aa-prototype/src/store/integrationActions.ts:266-317 (failure reasons, no NHI)`, `aa-prototype/src/apps/demo/DemoIntegrations.tsx:252-253,457 (raw HL7 view)`, `aa-prototype/src/apps/mobile/screens/MoreScreen.tsx:65`, `searched: restricted access\|rawPayload\|synthetic\|non-production in src -> none`
- **Verifier:** corrected from Partial. Verdict and size upheld. Dropped the reviewer's 'audit log stores NHI (intake.ts:118)' point: the audit trail is held in the core platform where the NHI lawfully lives and the requirement bars logs, errors and telemetry that leave it, so it is not a real defect. Confirmed failure reasons and console output carry no NHI. Narrowed the leak-scan gap to a nice-to-have demonstration.
