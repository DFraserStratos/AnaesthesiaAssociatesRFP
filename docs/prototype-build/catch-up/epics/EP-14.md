## FT-14.6 · Further hospital feeds and automatic matching · Partial

[FT-14.6](../../../../requirements-board/requirements/stories/FT-14.6.md) · [board](http://localhost:5180/#/board?item=FT-14.6) · status Proposed · surfaces: simulator, domain, store, seed, admin, demo-guide · confidence medium

- **Requirement:** After the core system runs with a manual matching review like today's, the remaining hospital feeds are added and matching is automated as a second phase. The first release already includes automatic sync from St George's and Southern Cross (US-02.1.5), which only brings rows in for admin decision.
- **Prototype today:** Integration messages from 3 feeds (STG, CPH, SX) are applied automatically through guarded actions (create/move/cancel Card, patient reuse by NHI, dedupe by MSH-10, dead-letter to admin monitor for failures). Surgeon PDF ingest samples exist for Forte Health and Christchurch Eye (admin reviews extracted rows). No manual matching screen, no unmatched queue, no feeds for Forte, Christchurch Eye, Burwood, Southern Endo or McMurray.
- **Missing or wrong:**
  - No feeds/hospital entries or canned daily sheets for Forte Health, Christchurch Eye, Burwood, Southern Endo, McMurray Centre (US-14.6.1).
  - No manual matching review baseline (US-02.1.2/02.1.5): auto-apply is the only path, so 'manual first, automate later' phasing cannot be shown. Depends on the EP-02 matching screen.
  - Child-level (US-14.6.2, not feature body): exceptions (failed/unmatched) go to a dead-letter/monitor list, not an admin match-or-reject queue; hospital-supplied Contract (OQ-22) is not set by feed messages.
- **Demo trigger:** Simulator (/demo/integrations): add feeds for Forte, Christchurch Eye, Burwood, Southern Endo, McMurray with canned daily-sheet messages. Once the EP-02 matching screen exists, a control-panel button 'Deliver hospital sheet' (shown only on the matching screen, per feed) drops rows into the matching queue, plus a demo-only 'Auto-match on/off' toggle on that screen so phase-2 behaviour (routine updates applied, exceptions left for admin) can be shown.
- **Evidence:** `aa-prototype/src/domain/integrations/feeds.ts:82-86 (only STG, CPH, SX)`, `aa-prototype/src/domain/integrations/pdfSamples.ts:101,129 (Forte, Christchurch Eye PDFs only)`, `aa-prototype/src/store/integrationActions.ts:306 processMessage`, `searched: Burwood\|McMurray\|Southern Endo in src -> none`, `searched: unmatched\|matching screen\|lastSynced in src -> none`

## US-14.4.1 · NHI lookup via Digital Services Hub · Partial

[US-14.4.1](../../../../requirements-board/requirements/stories/US-14.4.1.md) · [board](http://localhost:5180/#/board?item=US-14.4.1) · status Proposed · surfaces: domain, mobile, web, admin, shell, simulator, demo-guide · confidence high

- **Requirement:** System looks up and validates patients against the NHI FHIR API via the Health NZ Digital Services Hub when adding a Booking (web and mobile images show the lookup); anaesthetists referenced by HPI CPN; NHI used only for that purpose (HIPC 2020); NHI can be refreshed from the central register (hospitals get updates twice daily); Hub lookups part of dual-format regression.
- **Prototype today:** AddCardFlow/ManualCardForm: NHI field + 'Look up' button (disabled when empty unless a prefill exists). runLookup calls lookupNhi (normalises via validateNhi, then 6-entry canned map): hit fills name, DOB, phone, ethnicity with 'Found X. Patient details pre-filled, still editable'; miss says 'Not found in this demo's records. Enter the details manually.' Same form reused by web ListDetailView, mobile routes and admin PhoneAdviceBooking (S2 empty-NHI prefill of DEM1239 fills a whole booking). createCard -> upsertPatient rejects an invalid NHI at save and reuses an existing patient by NHI. NHI is never sent to Xero or shown on invoices (incidental support for purpose-only), and the Xero sim callout says so. No refresh path.
- **Missing or wrong:**
  - Invalid NHI (bad check digit / letters I, O) at lookup shows 'Not found', not a validation failure; validation surfaces only on save or in the integration monitor validator
  - Lookup limited to 6 canned NHIs; any other valid NHI cannot be shown as found
  - No Hub states: no loading, unavailable/timeout/error with fallback to manual entry
  - No refresh from the NHI register for existing patients, no last-refreshed time (twice-daily hospital cadence)
  - No explicit statement that NHI is used only for this purpose (HIPC 2020); only implicit via 'NHI never resides in Xero'
  - Anaesthetist HPI CPN reference not surfaced in the booking/lookup flow (stored as 'HPI id')
  - Hub lookup path not shown as part of dual-format regression in the UI (unit tests only)
- **Demo trigger:** Lookup already demoable via 'Look up' on Add booking (web, mobile, admin). Propose control-panel toggle 'Hub: Available / Slow / Unavailable' shown only while Add booking is open: Slow shows a loading state, Unavailable shows 'Hub unavailable, enter manually' with Retry. Plus 'Refresh from NHI register' button on admin patient/card detail that updates demographics from the Hub stub and stamps 'Last refreshed'.
- **Evidence:** `aa-prototype/src/shared/flows/ManualCardForm.tsx:76-103,146-160`, `aa-prototype/src/domain/nzhis.ts:81-119`, `aa-prototype/src/store/cardActions.ts:83-90`, `aa-prototype/src/shared/flows/AddCardFlow.tsx`, `aa-prototype/src/apps/web/screens/ListDetailView.tsx:237`, `aa-prototype/src/apps/mobile/routes.tsx:134`, `aa-prototype/src/apps/admin/flows/PhoneAdviceBooking.tsx:97`, `aa-prototype/src/apps/admin/screens/IntegrationMonitorScreen.tsx (validator tab)`, `searched: refresh.*nhi\|nhi.*refresh\|Privacy Code in src -> none`

## FT-14.4 · NZ identity standards · Partial

[FT-14.4](../../../../requirements-board/requirements/stories/FT-14.4.md) · [board](http://localhost:5180/#/board?item=FT-14.4) · status Proposed · surfaces: domain, admin, mobile, web · confidence high

- **Requirement:** Patient identity checked against the NHI FHIR API, anaesthetists referenced by HPI CPN, ethnicity coded to NZHIS Level 4; the identity standards Health NZ mandates, spoken by the integration from the outset.
- **Prototype today:** NHI: 'Look up' button on shared ManualCardForm with demo badge 'NHI FHIR lookup · Digital Services Hub' calling canned lookupNhi (6 fictional patients). validateNhi covers both NHI formats. HPI: Anaesthetist.hpiId (fictional 6-char ids) shown/edited only in admin Add ('HPI id (optional)') and Edit sheet header, and emitted as FHIR Practitioner identifier (HPI_SYSTEM) in the integrations simulator; extracted from inbound FHIR but display-only. Ethnicity: 12-code NZHIS L4 demo subset with validator and quarantine/data-quality queue. Integrations callout says NHI lookup/Keycloak are referenced, not implemented.
- **Missing or wrong:**
  - HPI labelled 'HPI id' everywhere (fieldLabels.ts:121, AddAnaesthetistFlow:72, EditAnaesthetistSheet:61); no 'CPN' naming, no CPN format check; not shown on any anaesthetist-facing or booking screen
  - NHI lookup resolves only 6 canned NHIs; any other valid NHI shows 'Not found'
  - Ethnicity coding is a curated 12-code subset of L4, not the full set (owned by US-11.1.1)
  - Inbound FHIR Practitioner HPI is ignored by the store effect (display-only)
- **Evidence:** `aa-prototype/src/domain/nzhis.ts:81-119 (canned lookupNhi)`, `aa-prototype/src/shared/flows/ManualCardForm.tsx:76-103,146-160`, `aa-prototype/src/domain/types.ts:148-149 (hpiId)`, `aa-prototype/src/shared/audit/fieldLabels.ts:121`, `aa-prototype/src/apps/admin/flows/AddAnaesthetistFlow.tsx:72`, `aa-prototype/src/apps/admin/flows/EditAnaesthetistSheet.tsx:61`, `aa-prototype/src/domain/integrations/fhir.ts:20,151,203-230`, `aa-prototype/src/apps/demo/DemoIntegrations.tsx (target-state callout)`
