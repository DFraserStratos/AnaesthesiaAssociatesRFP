# EP-14 · Health systems integration · gap details

Part of the [gap analysis](../GAP-ANALYSIS.md#ep-14) · catalogue `fbdd555` · [EP-14](../../../../requirements-board/requirements/stories/EP-14.md)

> EP-14 is mostly a parent of FT-14.1 to FT-14.6 (Future Work lane), but its body states three rules of its own: the first-release sync of both integrated hospitals into the matching screen, the NHI lookup being in scope, and the adapter and configuration-matrix design. The prototype's HL7/FHIR pipeline is already badged Future scope (catch-up Phase 14, to be demoted in Phase 34), so the Future-lane message is in place. The real gap is structural and sits in EP-02: there is no hospital download or matching screen (FT-02.1, US-02.1.5, Phase 33). Until then, integrationActions applyEffect writes hospital messages directly as Bookings onto Dr Souter's existing ACTIVE List. The first-release sync depends on that screen being built and on those messages being rerouted into it, which is also where the OQ-118 stub-at-intake question interacts. OQ-109 part 1 (St George's and Southern Cross vs Forte) is unresolved, so feed names may change, and part 2 is only assumed (4 Nov, not yet seen by AA). Demo impact: the S1 beat (MSG-STG-1001 lands Sarah Mitchell on Souter's Tue 28 Jul AM List) would gain an office review-and-merge step, and the 'Fire hospital message' triggers would change. S4's Christchurch Public mapping-fix beat stays but is framed as Future. The NHI lookup beat (S2) is unaffected.

## EP-14 · Health systems integration · Partial

[EP-14](../../../../requirements-board/requirements/stories/EP-14.md) · [board](http://localhost:5180/#/board?item=EP-14) · status Proposed (1) · surfaces: admin, simulator, domain, store, seed, demo-guide · confidence medium

- **Requirement:** St George's and Southern Cross (OQ-109) are integrated today and the first release syncs both into the matching screen (FT-02.1). More feeds, automatic matching, HL7 v2 and FHIR are Future Work; the NHI lookup is in scope as a simple API. Transport is an adapter over one queue/retry/translation path, with a maintained per-hospital matrix (v2 or FHIR, polled or pushed).
- **Prototype today:** Simulated integration tier: canned HL7 v2 and FHIR R4 messages from three feeds (St George's HL7, Christchurch Public HL7 misconfigured on purpose, Southern Cross FHIR) are stored, deduped, retried 3 times then dead-lettered or parked, and applied directly as Bookings onto an existing ACTIVE List of Dr Souter. The Admin Integrations Messages and Feed config tabs and the simulator page are badged Future scope, with a note that the in-scope path is a download into a matching screen. The NHI Look up in the manual booking form uses canned records. There is no matching screen and no hospital download intake; the only trace is a 'hospitalRow' draft origin type and a 'Hospital download' source label stamped by the interim HL7 create path.
- **Missing or wrong:**
  - No matching screen or review-and-merge intake for hospital downloads (FT-02.1, US-02.1.5). Hospital messages bypass it and write Bookings straight onto a List; integrationActions.ts:149,169 label this interim until Phase 33. DraftListsScreen has no hospital-row or matching content.
  - The first-release automatic sync of the two integrated hospitals is not shown as in-scope intake. The only HL7/FHIR UI is badged Future and used as the S1 path.
  - Which two hospitals are integrated is unresolved (OQ-109, St George's and Southern Cross vs Forte). Prototype feeds are St George's, Christchurch Public and Southern Cross.
  - No transport-adapter concept or per-hospital configuration matrix: the Feed config tab shows only transport (HL7 v2 or FHIR) and field mapping, with no polled vs pushed attribute or adapter switch.
  - Message routing is hardcoded to Dr Souter's 28/30 July Lists; an incoming booking is not matched to a List or anaesthetist.
  - The NHI lookup is canned and shown in the manual booking form only. It is not framed as a national-service API call from the integration tier (minor, adequate for demo).
- **Demo trigger:** Admin matching screen (built under FT-02.1): a 'Sync hospital downloads' demo button that pulls canned St George's and Southern Cross rows into it as unmatched candidates for review and merge. Integrations Feed config tab: a per-hospital matrix column 'Transport: HL7 v2 or FHIR, Polled or Pushed' with a 'Switch to push' demo toggle showing that only the adapter changes while queue, retry and translation stay the same.

## US-14.4.1 · NHI lookup via Digital Services Hub · Partial

[US-14.4.1](../../../../requirements-board/requirements/stories/US-14.4.1.md) · [board](http://localhost:5180/#/board?item=US-14.4.1) · status Proposed (1) · surfaces: domain, mobile, web, admin, shell, simulator, demo-guide · confidence high

- **Requirement:** System looks up and validates patients against the NHI FHIR API via the Health NZ Digital Services Hub when adding a Booking (web and mobile images show the lookup); anaesthetists referenced by HPI CPN; NHI used only for that purpose (HIPC 2020); NHI can be refreshed from the central register (hospitals get updates twice daily); Hub lookups part of dual-format regression.
- **Prototype today:** AddCardFlow/ManualCardForm: NHI field + 'Look up' button (disabled when empty unless a prefill exists). runLookup calls lookupNhi (normalises via validateNhi, then 6-entry canned map): hit fills name, DOB, phone, ethnicity with 'Found X. Patient details pre-filled, still editable'; miss says 'Not found in this demo's records. Enter the details manually.' Same form reused by web ListDetailView, mobile routes and admin PhoneAdviceBooking (S2 empty-NHI prefill of DEM1239 fills a whole booking). createCard -> upsertPatient rejects an invalid NHI at save and reuses an existing patient by NHI. NHI is never sent to Xero or shown on invoices (incidental support for purpose-only), and the Xero sim callout says so. No refresh path.
- **Missing or wrong:**
  - Invalid NHI (bad check digit / letters I, O) at lookup shows 'Not found', not a validation failure; validation surfaces only on save or in the integration monitor validator
  - Lookup limited to 6 canned NHIs; any other valid NHI cannot be shown as found
  - No Hub states: no loading, unavailable/timeout/error with fallback to manual entry
  - No refresh from the NHI register for existing patients, no last-refreshed time (twice-daily hospital cadence)
  - No explicit statement that NHI is used only for this purpose (HIPC 2020); only implicit via 'NHI never resides in Xero'
  - Anaesthetist HPI CPN reference not surfaced in the booking/lookup flow (stored as 'HPI id')
  - Hub lookup path not shown as part of dual-format regression in the UI (unit tests only)
- **Demo trigger:** Lookup already demoable via 'Look up' on Add booking (web, mobile, admin). Propose control-panel toggle 'Hub: Available / Slow / Unavailable' shown only while Add booking is open: Slow shows a loading state, Unavailable shows 'Hub unavailable, enter manually' with Retry. Plus 'Refresh from NHI register' button on admin patient/card detail that updates demographics from the Hub stub and stamps 'Last refreshed'.
- **Evidence:** `aa-prototype/src/shared/flows/ManualCardForm.tsx:76-103,146-160`, `aa-prototype/src/domain/nzhis.ts:81-119`, `aa-prototype/src/store/cardActions.ts:83-90`, `aa-prototype/src/shared/flows/AddCardFlow.tsx`, `aa-prototype/src/apps/web/screens/ListDetailView.tsx:237`, `aa-prototype/src/apps/mobile/routes.tsx:134`, `aa-prototype/src/apps/admin/flows/PhoneAdviceBooking.tsx:97`, `aa-prototype/src/apps/admin/screens/IntegrationMonitorScreen.tsx (validator tab)`, `searched: refresh.*nhi\|nhi.*refresh\|Privacy Code in src -> none`

## FT-14.4 · NZ identity standards · Partial

[FT-14.4](../../../../requirements-board/requirements/stories/FT-14.4.md) · [board](http://localhost:5180/#/board?item=FT-14.4) · status Proposed (1) · surfaces: domain, admin, mobile, web · confidence high

- **Requirement:** Patient identity checked against the NHI FHIR API, anaesthetists referenced by HPI CPN, ethnicity coded to NZHIS Level 4; the identity standards Health NZ mandates, spoken by the integration from the outset.
- **Prototype today:** NHI: 'Look up' button on shared ManualCardForm with demo badge 'NHI FHIR lookup · Digital Services Hub' calling canned lookupNhi (6 fictional patients). validateNhi covers both NHI formats. HPI: Anaesthetist.hpiId (fictional 6-char ids) shown/edited only in admin Add ('HPI id (optional)') and Edit sheet header, and emitted as FHIR Practitioner identifier (HPI_SYSTEM) in the integrations simulator; extracted from inbound FHIR but display-only. Ethnicity: 12-code NZHIS L4 demo subset with validator and quarantine/data-quality queue. Integrations callout says NHI lookup/Keycloak are referenced, not implemented.
- **Missing or wrong:**
  - HPI labelled 'HPI id' everywhere (fieldLabels.ts:121, AddAnaesthetistFlow:72, EditAnaesthetistSheet:61); no 'CPN' naming, no CPN format check; not shown on any anaesthetist-facing or booking screen
  - NHI lookup resolves only 6 canned NHIs; any other valid NHI shows 'Not found'
  - Ethnicity coding is a curated 12-code subset of L4, not the full set (owned by US-11.1.1)
  - Inbound FHIR Practitioner HPI is ignored by the store effect (display-only)
- **Evidence:** `aa-prototype/src/domain/nzhis.ts:81-119 (canned lookupNhi)`, `aa-prototype/src/shared/flows/ManualCardForm.tsx:76-103,146-160`, `aa-prototype/src/domain/types.ts:148-149 (hpiId)`, `aa-prototype/src/shared/audit/fieldLabels.ts:121`, `aa-prototype/src/apps/admin/flows/AddAnaesthetistFlow.tsx:72`, `aa-prototype/src/apps/admin/flows/EditAnaesthetistSheet.tsx:61`, `aa-prototype/src/domain/integrations/fhir.ts:20,151,203-230`, `aa-prototype/src/apps/demo/DemoIntegrations.tsx (target-state callout)`
