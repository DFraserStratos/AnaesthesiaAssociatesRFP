# EP-13 · Admin oversight and master data · gap details

Part of the [gap analysis](../GAP-ANALYSIS.md#ep-13) · catalogue `a68f09b` · [EP-13](../../../../requirements-board/requirements/stories/EP-13.md)

> Core structural change: Surgeon.roomId (single) becomes a many-to-many surgeon-room link (OQ-128 answered 4 Nov by Donald for the build). This ripples to surgeonsInRoom, SurgeonFields and SurgeonEditSheet (multi-select), SurgeonProfile (several room cards), the Surgeons table Room column, seed (cast.ts, specialistDirectory.ts, which currently gives a two-practice surgeon the smaller room only), a PERSIST_VERSION bump, surgeon master/action tests and screenshot captures. Separately, room contactEmail must become optional (cleanRoomFields currently refuses blank; the seed injects reception@ placeholders), and the booking update email drafter (US-02.3.3) and missing-NHI email (US-11.1.5) must tolerate an empty To. Practice manager/PA contacts (US-13.6.5) are a new child entity; OQ-127 leaves it open whether it hangs on the room or the surgeon, so model it as a contact with an optional room or surgeon owner. Open questions OQ-126 (address book/specialty search/street address), OQ-127 (which room's contacts apply to a multi-room Booking) and OQ-129 (surgeons without HPI CPN; the cutover load US-13.4.3 depends on it) make parts speculative; grades follow the written text, and the one-room model and mandatory room email are the only implemented behaviours now contradicted. Sequencing: do the multi-room/optional-email model change in one phase first (covers FT-13.6, US-13.6.1, most of US-13.6.2), then PA contacts. The demo guide beats that show a single room card on a surgeon profile would change slightly. No demo trigger needed: all of it is direct admin UI. Verification changed FT-13.6 and US-13.6.2 from Partial to Contradicts; US-13.6.1 and US-13.6.5 are upheld.
