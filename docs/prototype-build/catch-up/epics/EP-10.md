# EP-10 · Payments, disbursement and AA fees · gap details

Part of the [gap analysis](../GAP-ANALYSIS.md#ep-10) · catalogue `fbdd555` · [EP-10](../../../../requirements-board/requirements/stories/EP-10.md)

> Structural: the main EP-10 issue is that the prototype treats paying the anaesthetist as an in-system action (admin 'Run payables', Xero-sim 'Pay now', actor 'Payables run'). FT-10.2, US-09.2.4 and OQ-111 (answered 4 Nov) say Xero's payables run makes the payment and the engine detects and records it. The fix is to move the payout into the Xero simulator as a badged demo action, add webhook and poll detection of an ACCPAY payment, and turn the Admin monitor card into read-only tracking. The disbursement actions (runPayables, disbursePayable) have exactly two callers (BillingMonitorScreen, DemoXero), so the change is contained. Closely tied to US-09.2.4 in EP-09. Dependencies: US-10.2.7 (weekly payment cycle, Proposed, OQ-47 open; Greg now proposes Monday to Sunday week, Thursday payment) is not built (no ISO week, close or reconciliation step) and sits outside this item list; US-10.2.6 and the 'next payables run' wording of US-10.2.1 depend on it. Whether BCTI approval equals release is part of OQ-47. BCTI count and period (OQ-29, one per payment or per weekly run) would change the per-procedure ACCPAY model US-10.2.6 relies on. Prepayments and the AA Holding account are not modelled in UI at all (only comments), so prepaid money can currently be disbursed like any other; that belongs to the EP-06/08 prepayment work but bears on the one-path story. AA fee never netted (US-10.3) is unaffected. Demo-script impact: S3 Beat 3 (03-demo-script.md ~519-531) and S4 part-payment steps (~652-655: Run payables, Payment received full, Run payables again), 02-workflows Workflow 7 step 6, and 01-personas 'Run disbursements' use the in-app Run payables button; re-homing to a Xero simulator action changes those beats. A bulk-remittance tab (US-10.2.4) is additive to the Xero sim only. US-10.2.1 and US-10.1.1 need no code change. Any seed-shape change needs a PERSIST_VERSION bump (currently 26).

## FT-10.2 · Releasing payables · Contradicts

[FT-10.2](../../../../requirements-board/requirements/stories/FT-10.2.md) · [board](http://localhost:5180/#/board?item=FT-10.2) · status Verify (3) · surfaces: admin, simulator, store, domain, demo-guide · confidence high

- **Requirement:** Once a receivable is paid, its matching payable is authorised for the next payables run, so the anaesthetist is paid only what AA has received. The payment is made in Xero's payables run; the system records and tracks it (US-09.2.4) and does not make the payment itself (OQ-111).
- **Prototype today:** receivePayment authorises the DRAFT ACCPAY for exactly the cumulative amount received (DRAFT to AUTHORISED). The admin Billing monitor has an unbadged 'Run payables' card and button (runPayables) that disburses authorised minus disbursed, writes a Disbursement and marks the case Disbursed, as system actor 'Payables run'; the source comment calls it product UI, not a simulation. The Xero sim's PairDetail has 'Simulate payment and payout' / 'Pay <anaesthetist> now', which calls receivePayment then disbursePayable(OFFICE_ACTOR). Nothing detects a disbursement made in Xero (reconciliationPoll and the webhook path handle ACCREC receipts only; no ACCPAY-paid event). No weekly cycle, ISO week, close or payment day anywhere.
- **Missing or wrong:**
  - WRONG: the payment to the anaesthetist is made by the system (Admin 'Run payables' and Xero-sim 'Pay now' both call store disbursement actions, audited as a system/office action); the requirement says Xero's payables run makes it and the engine detects and records it
  - The payables run is unbadged product UI in Admin, not a Xero action; no 'Xero payables run' simulation followed by webhook/poll detection of the ACCPAY payment (the US-09.2.4 side)
  - No payment-cycle notion (ISO week, Friday close, Monday reconciliation, payment day); the cycle is Proposed and OQ-47 is open (Greg's latest: Monday to Sunday week, Thursday payment), so this is a note to track rather than a hard gap
  - Release rule itself (authorise exactly the cumulative amount received, remainder stays on the receivable) is correct and matches
- **Demo trigger:** Re-home the payout as a Xero simulation: on /admin/billing and /demo/xero a badged (Demo simulation) button 'Run Xero payables run' that pays every authorised ACCPAY in the simulated Xero and then fires the payment webhook (plus the existing 'Run reconciliation poll' as catch-up for a missed one) so the engine records the Disbursement; the Billing monitor 'Run payables' card becomes read-only tracking ('Awaiting Xero payables run: n payables, $x'). Optionally show the current ISO payment week beside it once OQ-47 settles.
- **Evidence:** `aa-prototype/src/store/paymentActions.ts:96-100,143-165 (ACCPAY authorised for payableReleasedFor(newReceived))`, `aa-prototype/src/store/payablesActions.ts:1-10,19,56-140,147-169 (runPayables/disbursePayable disburse as 'Payables run' system actor; header says unbadged office action, not a simulation)`, `aa-prototype/src/apps/admin/screens/BillingMonitorScreen.tsx:54-64,125-146 ('Payables run' card and 'Run payables' button)`, `aa-prototype/src/apps/demo/DemoXero.tsx:228-262,286-303 (settleInvoice: receivePayment then disbursePayable; 'Pay <anaesthetist> now')`, `aa-prototype/src/store/index.ts:303-304 (only two callers of the disbursement actions: BillingMonitorScreen and DemoXero)`, `searched: ISO week\|payment cycle\|weekly\|Friday in src -> none; reconciliationPoll.ts has no payable/disburs handling`

## US-10.2.6 · Approve the period's BCTIs for payment · Partial

[US-10.2.6](../../../../requirements-board/requirements/stories/US-10.2.6.md) · [board](http://localhost:5180/#/board?item=US-10.2.6) · status Verify (3) · surfaces: admin, store, domain · confidence medium

- **Requirement:** Once AA has generated the BCTIs for a payment period, they are approved for payment before being paid out; BCTIs not yet approved are not in the payment run. Who approves and how is unknown and may simply be the US-10.2.1 release.
- **Prototype today:** Each ACCPAY (the BCTI, one per procedure) starts DRAFT and becomes AUTHORISED automatically when its receivable is paid; runPayables and payablesDue include only authorised minus disbursed amounts, so an unapproved (DRAFT) payable is never in the run. No approval list or approve action, no payment-period grouping, no 'approved for payment' wording; Xero sim shows Authorised/Disbursed amounts only.
- **Missing or wrong:**
  - No explicit 'approved for payment' state or step distinct from authorisation, and no admin or system approve action for a period's BCTIs
  - No payment period (ISO week or month) batching BCTIs for approval (depends on the unbuilt weekly cycle, US-10.2.7)
  - Approval is purely a side effect of receipt; nothing tells a presenter 'not approved, so not in this run'
  - If approval is settled as the same step as US-10.2.1 authorisation, only labelling (BCTI approved for payment, excluded-from-run list) is missing
- **Demo trigger:** Existing: Demo actions > 'Payment received · full' releases (approves) a payable. If a separate approval is kept after OQ-47: an 'Approve this week's BCTIs' control on the Billing monitor payables card that moves the period's released payables to Approved for payment, listing unapproved ones as excluded from the run.
- **Evidence:** `aa-prototype/src/store/xeroHandoff.ts:276 (ACCPAY created status 'draft')`, `aa-prototype/src/store/paymentActions.ts:149-150 (draft to authorised on receipt)`, `aa-prototype/src/store/payablesActions.ts:36-47,147-158 (run takes only authorised minus disbursed)`, `aa-prototype/src/domain/billing/bcti.ts (BCTI = the procedure ACCPAY; no period approval)`, `searched: approv.*BCTI\|approved for payment in src -> none`

## US-10.2.5 · Negative invoices netted in the payment run · Missing

[US-10.2.5](../../../../requirements-board/requirements/stories/US-10.2.5.md) · [board](http://localhost:5180/#/board?item=US-10.2.5) · status Agreed (4) · surfaces: domain, store, seed, admin, web, mobile, demo-guide · confidence high

- **Requirement:** A negative invoice (refund or credit after invoicing) is netted against the anaesthetist's positive payables in the next payment run (19 positive + 1 negative = pay net); remittance advice shows the negative netted against the positives.
- **Prototype today:** Nothing. buildInvoicesForBooking refuses a negative group total as 'negativeTotal'; runPayables disburses only positive authorised increments, one Disbursement per ACCPAY; no credit note, refund, netting or remittance entity; anaesthetist apps have no remittance view.
- **Missing or wrong:**
  - No negative invoice / credit-driven negative payable entity
  - Payment run does not net negatives against positives; pays per payable, not a per-anaesthetist net total
  - No remittance advice (per run, per anaesthetist) in web, mobile or admin
  - No demo way to create a refund/credit after the anaesthetist is paid
  - Depends on credit-after-invoicing flow US-08.6.2 (absent) as the source of the negative
- **Demo trigger:** Button 'Raise credit on a paid invoice' on the admin invoice detail (creates a negative invoice to the anaesthetist), then 'Run payables' on Billing monitor pays the net and shows a Remittance advice panel (invoices, negative netted, net total) in Admin and Dr Souter's Web Accounts.
- **Evidence:** `aa-prototype/src/domain/billing/invoiceBuild.ts:409-423 (negativeTotal refused)`, `aa-prototype/src/store/payablesActions.ts:49-150 (per-ACCPAY increment, no netting)`, `aa-prototype/src/domain/billing/validateBookingForBilling.ts:233-241 (negative fee blocked)`, `searched (re-run): remittance\|refund\|credit note\|netting\|negative in src (non-test) -> only comments, negativeTotal guard, CSS margins, a DemoXero comment about remittance matching key`

## US-10.2.7 · Weekly payment cycle · Missing

[US-10.2.7](../../../../requirements-board/requirements/stories/US-10.2.7.md) · [board](http://localhost:5180/#/board?item=US-10.2.7) · status Proposed (1) · surfaces: admin, web, store, domain, seed, shell, simulator, demo-guide · confidence high

- **Requirement:** Payments run on a weekly cycle named by ISO week (Friday ledger close/snapshot/reconcile, Monday office working day, Tuesday payment schedule to the accountant, anomalies rolled into next cycle). A payment is shown against its cycle's week number; an anomaly not fixed by Tuesday is held out of this cycle's schedule and rolled forward. Status Proposed, still to confirm with accountant (OQ-47).
- **Prototype today:** Nothing for the cycle. runPayables creates Disbursements with payablesRunId (PR####) and clock time only (types.ts:824). ISO week number appears only as a label in the admin RightRail (RightRail.tsx:60,128), unrelated to payments. Demo clock is fixed at Tuesday 21 July 2026 8:00; no advance control found.
- **Missing or wrong:**
  - No payment cycle/week entity or ISO week label on runs, disbursements, or the web/admin payment lists
  - No Friday close/snapshot/bank reconciliation step
  - No Monday anomaly list or ability to hold a payable out of the run and roll it to next cycle
  - No Tuesday payment schedule (view/export for accountant)
  - Run payables not tied to a cycle day; seeded historical disbursements have no week
  - Payment lookup does not show week number (acceptance criterion 1 unmet)
- **Demo trigger:** Billing monitor 'Payment cycle' panel for week N with control-panel buttons shown only there: 'Close week (Friday)' snapshot+reconcile, 'Flag anomaly' on a payable (held), 'Build Tuesday schedule' (held items roll to week N+1), then Run payables pays the schedule and stamps the week number; web Payments and admin payment lists show 'Week N'.
- **Evidence:** `searched: isoWeek\|payment cycle\|accountant\|anomal\|friday\|roll(ed) forward in aa-prototype/src non-test -> only RightRail week label and unrelated canvas.rollForward`, `aa-prototype/src/store/payablesActions.ts:55-153`, `aa-prototype/src/domain/types.ts:819-826`, `aa-prototype/src/apps/admin/screens/BillingMonitorScreen.tsx:121-141`, `docs/prototype-build/catch-up/analysis/domain-model-delta.md DM-25 (same finding)`

## US-10.2.4 · Bulk remittance stays in Xero · Missing

[US-10.2.4](../../../../requirements-board/requirements/stories/US-10.2.4.md) · [board](http://localhost:5180/#/board?item=US-10.2.4) · status Proposed (1) · surfaces: simulator, store, demo-guide · confidence medium

- **Requirement:** Bulk hospital payments covering multiple invoices are matched by Xero's own bank reconciliation and remittance add-on, not the Billing/Invoice Engine; any item the add-on cannot match stays as an unmatched item in Xero's bank reconciliation for the office to handle there.
- **Prototype today:** Nothing that shows it. Payments reach the engine only as single-invoice webhook or poll events (full or half). The only related text is Xero-sim copy that the engine's InvoiceNumber is the key hospitals and insurers quote on remittances so remittance matching can key on it. Xero sim has Contacts and Invoices tabs only. The engine does no bulk matching (consistent with the requirement), but nothing shows Xero doing it or the unmatched leftovers.
- **Missing or wrong:**
  - No simulated bank feed or Xero bank reconciliation view
  - No bulk payment covering several invoices (one bank line, several ACCRECs) that Xero's add-on matches by reference and amount before the engine sees it
  - No unmatched line left in Xero for the office, and no 'what to do' hint for a receipt with no reference
- **Demo trigger:** On /demo/xero add a 'Bank reconciliation' tab and a badged (Demo simulation) button 'Receive bulk hospital payment': one bank line covering three open ACCRECs from the same hospital, matched by the remittance add-on (reference and amount) so the engine then receives three normal payment events, plus one bank line with no reference left 'Unmatched in Xero' for the office. Optional second button 'Office matches line'.
- **Evidence:** `aa-prototype/src/apps/demo/DemoXero.tsx:66,548,718 (InvoiceNumber as remittance matching key; copy only)`, `aa-prototype/src/shared/demoTriggers/registry.ts:548-578 (payment triggers are single-invoice only)`, `searched: remittance\|bank reconcil\|bank feed\|unmatched in src -> only DemoXero copy; 'unmatched appointment' integration wording is unrelated`
