## Start here

- **[index.html](index.html)** is the build plan page: themes, the gap at a glance, every phase with
  its kick-off prompt (copy, paste into a fresh Claude Code session).
- **[ROADMAP.md](ROADMAP.md)** is the phase list, dependencies and milestones.
- **[phases/](phases/)** has one detailed plan per phase (`phase-NN-<slug>.md`) and its kick-off prompt
  (`phase-NN-<slug>.prompt.md`).
- **The UI unification track (U1 to U7)** is owner-added and outside the gap analysis: seven phases
  (`phases/phase-U1-...` to `phase-U7-...`) that make one hand-built component per job, from the audit
  and plan in [`docs/ui-unification/`](../../ui-unification/README.md). They run between the catch-up
  phases (ROADMAP.md, "Sequencing rules", first rule). `/update-build-plan` must keep them.
- **[GAP-ANALYSIS.md](GAP-ANALYSIS.md)** is the verified gap analysis: summary, counts, everything Missing,
  structural (data model) changes, prototype behaviour to remove, and per-epic gap tables.
  **[epics/](epics/)** has the full detail for every gap, one file per epic.

## Files

| Path | What it is |
|---|---|
| `gaps.json` | Machine-readable gap data: every in-scope item's verdict, what is missing or wrong, evidence, demo trigger, size; plus `dataModelDeltas` (DM-nn), `reverseFindings` (RV-nn), `themes`. |
| `analysis/prototype-map-*.md` | An index of the prototype's code by area (screens, store actions, domain types, seed, harness bar). Useful to any build session. |
| `analysis/domain-model-delta.md` | DM-nn: structural differences between the catalogue's model and the prototype's. |
| `analysis/reverse-check.md` | RV-nn: retired or superseded behaviour the prototype still has, and old Decisions-log rulings the catalogue now overrides. |
| `plan.json` | The phase outline as data (feeds `index.html`). |
| `status.json` | Optional build status for `index.html`: a phase in progress before its `PROGRESS.md` row exists, and what runs next. `PROGRESS.md`'s status table wins once it has the row. |
| `units.json` | Generated by `assemble-gaps.mjs`: every gap, DM and RV id the plan must place in a phase or park. |
| `plan.config.json` | This plan's settings for the `update-build-plan` tools: plan name, the prototype's folders, `PROGRESS.md`, first phase 14, the Future Work lane, capture, the agents' project text and this page's words. |

The scripts and workflows that produced all of the above are the `update-build-plan` skill's tools, in
`requirements-board/agent/skills/update-build-plan/tools/` (`T` below). They find this plan by its
`plan.config.json`.

## How it was made

1. **Gap analysis** (`T/workflow-gap-analysis.js`, Sonnet): six agents mapped the prototype code; one
   compared the data model; one reviewer per epic graded every in-scope item (272; retired items and the Future Work lane
   excluded) against the maps and the code; a separate adversarial verifier re-checked each epic's
   gradings from scratch (34 corrected); a reverse check looked for retired or superseded behaviour;
   a themes agent wrote the summary. `T/assemble-gaps.mjs` then built `gaps.json`,
   `GAP-ANALYSIS.md` and `epics/` directly from the agents' results.
2. **Development plan** (`T/workflow-dev-plan.js`, Opus): an architect outlined the phases, a script
   checked that every gap, DM and RV item lands in exactly one phase (or is parked with a reason), a
   critic challenged the outline, then one writer and one reviewer per phase produced the phase docs and
   prompts, and `T/build-index.mjs` renders `index.html` from `plan.json`.

## When the catalogue changes

Two skills from the Requirements Board kit (in `requirements-board/agent/skills/`, linked from
`.claude/skills/`) run the whole loop:

1. **`/update-requirements`** after a meeting or a round of board answers: files transcripts and notes as
   a catalogue note, completes answers that point at the evidence, updates the requirements, and writes a
   change log in `requirements-board/requirements/changes/`. Then commit and push.
2. **`/update-build-plan <commit or link>`** then re-grades the changed items against the prototype,
   re-plans the affected phases, updates their docs and prompts, moves the drift-check baseline and
   regenerates `index.html`.

Every phase also starts with its own drift check against the plan's baseline commit
(`node T/plan-state.mjs --diff <IDs>`, rename-aware across the catalogue's move), so small changes are
caught at build time.

The tools the second skill drives, all run from the repo root as `node T/<tool>`:

| Tool | What it does |
|---|---|
| `plan-state.mjs [--to <ref>] [--coverage] [--diff [IDs]]` | Baseline, what changed since (items, questions, notes and change logs added, domain model; rename-aware via `req-changes.mjs`, tested by `npm run test:plan-state`), built and in-progress phases, coverage check; `--diff` is the phase drift check. |
| `regrade-ids.mjs <ref> [--ids-only]` | The items to re-grade: changed in substance (not just links, sources, artifacts, order, swimlane or images) or added, plus the `affects` of changed questions, less retired items and the Future Work lane; with the counts and the share of in-scope items. |
| `build-args.mjs [ID ...]` | The `epics` args for the gap-analysis workflow (all in-scope items, or just those IDs). |
| `workflow-gap-analysis.js` | Sonnet reviewers + adversarial verifiers; `reuseMaps`, `runDelta`, `runReverse`, `runThemes` switches for partial re-runs. |
| `assemble-gaps.mjs <journal> <commit> <date> [--merge]` | Builds `gaps.json`, `GAP-ANALYSIS.md`, `epics/`, `units.json` from a run; `--merge` keeps earlier gradings for items not re-run. |
| `workflow-dev-plan.js` | Opus planners for a plan from scratch. |
| `workflow-plan-outline.js` | Opus architect and critic for an update: outline, ROADMAP, coverage, and a tier for each affected phase (light, substantive, hard). |
| `phase-briefs.mjs <outline journal> <sha> --out <dir>` | One brief per phase to write (its changes, diffs, gap entries, gating decisions, screenshot rows), the neighbours' outline, and the detail workflow's args. |
| `workflow-plan-detail.js` | Sonnet writers (Opus for hard phases) update the phase docs from their briefs; Sonnet reviewers check substantive ones on the diff. Re-run failures by passing the failed phases. |
| `apply-plan-update.mjs <outline journal> [<detail journals>] <commit> [--built ..]` | Rebuilds `plan.json` exactly from the runs, moves the baseline on baseline lines only (built and in-progress phases keep theirs), regenerates `index.html`. |
| `config.mjs [--json]` | The resolved `plan.config.json` (defaults filled in): the `config` argument of every workflow. |
| `build-index.mjs` | Renders `index.html` from `plan.json`, `gaps.json` and the prompt files. |
| `recipe-status.mjs [<phase> ...] [--plan-file <file>] [--check]` | The capture recipes behind each phase's catalogue screenshots; `--check` confirms every unbuilt phase doc and prompt carries the Catalogue screenshots step (ROADMAP.md). |
