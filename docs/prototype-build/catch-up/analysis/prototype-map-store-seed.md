# Prototype map: store + seed

Paths are under `aa-prototype/src/` unless stated. Facts are from reading the code (2026-10-20, PERSIST_VERSION 25). This area has NO routes or screens of its own: it is the Zustand store (`store/`) and the deterministic seed (`domain/seed/`). Screens are mapped by other agents; section 9 lists which screen files call each action so you can jump there.

Orientation. One Zustand store (`store/appStore.ts`) holds seeded domain state (masters, schedule = slots/lists/bookings/procedures/billingLines/warningClearances/availabilitySeries, audit, settings, appSettings, dashboards, dayNotes, officePrivate, notifications, counters) plus clock, billing, xero, integrations and shell slices. Every domain write goes through `mutate()` (`store/mutate.ts:188`), which in one `setState` applies the patch, re-runs the conflict rule, appends AuditEntries and stamps the touched Booking. Guards/actions are plain functions `(api, actor, ...) => Outcome` (refusals are data, never throws). Time is the demo clock (pinned 2026-07-21 08:00), randomness is hashed/seeded. The seed is built once at module load (`domain/seed/index.ts:~636`) and shared.

## 4. Lifecycle guards (`store/lifecycle.ts`)
State machine: `ACTIVE -> SUBMITTED -> AUTHORISED`, strictly ordered, NO Returned state anywhere; `DRAFT` is a pre-assignment state (no anaesthetist) and never submits/authorises/bills.
- `editRefusal(actor, list)` `:50`: the edit-rights matrix used by every Booking/Procedure/billing-line/attachment/patient write. Refuses: removed Draft List (`listRemoved`); AUTHORISED for everyone (`listAuthorised`); integration actor unless ACTIVE (`integrationImmutable`); anaesthetist on a DRAFT List (`notOwnList`), on another's List (`notOwnList`), on non-ACTIVE (`listSubmitted`); office/system may edit DRAFT, ACTIVE, SUBMITTED.
- `completionBlockersFor(state, booking)` `:100`: only `validateBookingForBilling` failures (code `validationFailed`, details = failure list) or `missingContext`; warnings (prepayment) never block (D5).
- `completeBooking` `:121`: refuses notFound, `bookingCancelled`, `integrationForbidden`, edit rights, `listNotActive` (Draft: "Assign an anaesthetist first."), `alreadyCompleted`, blockers. Audit `booking.complete`.
- `uncompleteBooking` `:172` ("Amend"): `bookingCancelled`, `notCompleted`, `integrationForbidden`, edit rights. `booking.uncomplete`.
- `submitList` `:221`: Draft -> `listNotActive`; not ACTIVE -> `listNotActive`; integration/system -> `submitForbidden`; anaesthetist not owner -> `notOwnList`; any non-cancelled uncompleted Booking -> `bookingsNotCompleted` (details = ids). `list.submit`.
- `authoriseList` `:275`: Draft/not SUBMITTED -> `listNotActive`/`listNotSubmitted`; non-office -> `officeOnly`. `list.authorise`; then emits `listAuthorised` (billing run + Xero handoff wired in `main.tsx`).
- `logListNote` `:321`: office only, text required, any List state; appends `phoneNotes`; `list.phoneNote`.
- `cancelBooking` `:362`: reason required, `alreadyCancelled`, edit rights; soft cancel stores `cancellation{reason,by,role,source,atISO}`; `booking.cancel`. Cancelled Bookings excluded from validation/billing/submit.
- `editBooking` `:416`: only `scheduledTime` and `notes` pass (attachments via attachment actions). `booking.update`.
- `editProcedure` `:452`: arbitrary Procedure patch (no field validation here), edit rights; `procedure.update`. Capture cards, billing-setup sheets and demo samples all use it.
- `editList` `:507`: patch hospitalId/surgeonId/notes only (never clear hospital/surgeon: `pairingRequired` via `pairingIssues`); edit rights; office surgeon change to a not-preferred pairing is never refused and adds `list.pairingAcknowledged` meta in same commit (anaesthetist edits never read preferences); a hand edit drops `recurringBookingId`. `list.update`.
- `reassignBooking` `:574`: moves one Booking between Lists; AUTHORISED either side refused (`listAuthorised`); integration only ACTIVE to ACTIVE; anaesthetist only own ACTIVE Lists; `sameList`; removed/missing target -> notFound. `booking.reassign`.

## 6. Derived rules in the store layer
- Conflicts (`domain/conflicts.ts`, `store/conflictReconcile.ts`): derived, never written by actions. A List conflicts if (`holiday`) its hospital is closed that date, or (`availability`) its Slot has a closed status (any non-bookable status, keyed by status key). AUTHORISED Lists and backdrop Lists never conflict; Draft Lists can carry holiday conflicts only. Soft warning, never a block. Office can clear (`conflictClears`) and re-flag. Reconcile runs inside every `mutate`, over Lists whose facts the patch touched (changed List/Slot, holiday add/remove, status master change); seed ends with `reconcileAllConflicts`.
- Warnings (`domain/warnings/`, `store/warnings.ts`): derived per Booking from `WarningFacts`; one rule registered, `prepaymentUnpaid` (`rules/prepaymentUnpaid.ts`): prepaymentStatus required -> strong "Prepayment required..."; outstanding -> strong "Prepayment invoice unpaid...". Only stored state: `schedule.warningClearances` (office `clearWarning:174`, `alreadyCleared`). Selectors `warningsForBooking/List`, `openWarnings`, `warningSummaryByList`. No guard reads warnings. Settings per rule in `appSettings.warningRules` (no screen edits them).
- Prepayment status `selectors.ts:639` `prepaymentStatusFor`: none | required | outstanding | paid; required iff a non-cancelled procedure is route billableParty + category `selfFundedPrepayment`; paid if case received >= invoice total (money, not label).
