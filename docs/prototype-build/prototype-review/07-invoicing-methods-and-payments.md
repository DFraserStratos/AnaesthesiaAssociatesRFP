## Findings

### 07.1 - Contract price rows cannot be keyed by surgeon in the UI  [PARTIAL]
- **RFP says:** "a need for an 'agreed fee' or 'contract price list' entity that can override or bypass the RVU calculation entirely for matching Cards, keyed by some combination of contract holder, surgeon, and/or procedure type" (line 1147), illustrated by "an agreed fixed-fee list negotiated directly with a particular plastic surgeon for their standard procedure set" (line 1141).
- **Built:** `ContractPrice` carries `contractId`, `rvgBaseCode`, `surgeonId` and `procedureOrdinal`, and `matchContractPrice` scores all four with most-specific-match-wins - `aa-prototype/src/domain/billing/contracts.ts:77-108`. The surgeon case is covered a second way, by holder: the seeded bariatric Type 3 is held by Mr Doyle and bills him - `aa-prototype/src/domain/billing/invoiceBuild.ts:192-213`.
- **Gap:** the office price-row editor offers only "Any code" / ordinal / price - there is no surgeon control - `aa-prototype/src/apps/admin/flows/ContractEditSheet.tsx:275-283`, and no seeded `ContractPrice` sets `surgeonId` (`grep -rn "surgeonId" src/domain/seed/contracts.ts` returns nothing). So the surgeon-keyed price row is engine-only and never seen or exercised in the demo. Separately, "procedure type" is represented by `rvgBaseCode`, a logged demo simplification (Decisions log, 5th external review #3).
- **Would a workshop audience notice:** unlikely. The RFP's plastic-surgeon example is satisfied visibly by the surgeon-held bariatric contract with its own fixed-price list, which the demo does exercise end to end. Only a vendor reading the price-list keys line by line would ask.
- **Severity:** cosmetic

### 07.2 - No office-side per-anaesthetist ledger view  [PARTIAL]
- **RFP says:** "While the invoice is addressed to the 'patient', the internal accounting revolves around the Anaesthetist. The agency (AA) is concerned with the billing in terms of each anaesthetist's 'ledger' position: what is owing and what is owed." (lines 1382-1386)
- **Built:** the model is anaesthetist-centred throughout. Every invoice document states "Billed by Anaesthesia Associates as agent for Dr X" (`aa-prototype/src/apps/admin/screens/InvoiceDocument.tsx`, visible in `a8-03-contract-holder-doc.png`); each BillingCase carries the two money axes; ACCPAYs carry the anaesthetist as payee; and the anaesthetist surfaces show both halves of the position - mobile Balances shows "Outstanding to you" over a flat ACCPAY list (`aa-prototype/src/apps/mobile/screens/BalancesScreen.tsx:52-63`), the web app shows receivables aging, overdue accounts and the GST activity list (`aa-prototype/src/store/selectors.ts:658-733`, screenshots `w-09-overdue.png`, `w-10-gst.png`).
- **Gap:** the admin app has no per-anaesthetist ledger screen. The billing monitor groups by List (anaesthetist name as a heading only - `aa-prototype/src/apps/admin/screens/BillingMonitorScreen.tsx:163`), the Invoices table has no anaesthetist column or filter (`grep -n "anaesthetist" src/apps/admin/screens/InvoicesScreen.tsx` returns one comment), and the payables run reports a single aggregate "$X to disburse to anaesthetists" rather than a per-anaesthetist breakdown (`aa-prototype/src/apps/admin/screens/BillingMonitorScreen.tsx:124-128`). The only office-visible per-anaesthetist money is the Payee column in the demo-badged Xero simulator. No REQUIREMENTS ID asks for an office ledger view, so this is an un-scoped RFP paragraph rather than a dropped work item.
- **Would a workshop audience notice:** only if asked directly ("show me Dr Souter's position from AA's side"). The presenter can answer from the anaesthetist app plus the payables card, but not from one office screen.
- **Severity:** cosmetic

### 07.3 - The no-double-charge rule is enforced at the engine, not by locking the flag  [PARTIAL]
- **RFP says:** "This is a hard constraint the billing engine must enforce structurally, not just as a UI hint - for example, by preventing a base-unit field from being editable on any procedure flagged as 'additional' within a split-billing episode." (lines 1210-1213)
- **Built:** the strong form of the rule is present. `splitBillingUnits` charges time units only for `isAdditional`, so stored base or modifier units are irrelevant to the fee (`aa-prototype/src/domain/billing/fee.ts:107-109`, test `fee.test.ts:62`); the Type 3 path refuses an ordinal-agnostic fixed price for an additional procedure for the same reason (`fee.ts:206-214`); and the UI disables the B and M steppers, the "use seeded value" reset, the ASA selector and the modifier chips, with the caption "Not charged on an additional procedure" plus a banner (`aa-prototype/src/shared/capture/UnitsCard.tsx:54-81`, `BtmCaptureBlock.tsx:164-171`).
- **Gap:** the *flag* is not locked in the store. `ProcedurePatch = Partial<Omit<Procedure, 'id' | 'cardId'>>` (`aa-prototype/src/store/lifecycle.ts:443`), so `editProcedure` would accept `{ isAdditional: false }` or a `baseUnitsCaptured` override on an additional procedure. No UI path sets either (`grep -rn "isAdditional" src` shows only reads outside `cardActions.ts`'s creators), and PROGRESS records the deliberate choice that read-only-when-completed is UI-level (Decisions log, `uncompleteCard` entry), so nothing in the demo can reach it. Recording it as a real-build hardening item, not a demo defect.
- **Would a workshop audience notice:** no. There is no reachable path, and the fee is correct even if the stored units were wrong.
- **Severity:** none

## Deliberate exclusions in this section

- **Real email sending.** REQUIREMENTS §10 excludes email; B6 defines despatch as "preview + mark-sent". The invoice document's "Email invoice" stamps `emailedAtISO` and audits it - `aa-prototype/src/store/billingRun.ts:398`.
- **PDF generation.** §10 excludes PDF libraries; "printable" is browser print of the on-screen document, isolated by a print stylesheet (Decisions log 2026-07-23, Phase 08 decision 7). Screenshot `a8-05-print-preview.png`.
- **Real OCR.** §10 excludes real OCR; the photo path uses two bundled sample cards with canned extractions (Decisions log 2026-07-23, "Sample paper cards are inline SVG data URLs").
- **Bulk billing volume.** N4 / §10: the RFP's ~28k invoices a year is narrated as seeded aggregate counters in the Xero sim archiving callout, not simulated (Decisions log, 5th external review #11).
- **Credit notes for an over-collected pre-payment.** Phase 09 review decided an over-prepaid full pre-payment fails the Card to the monitor via the `negativeTotal` belt rather than issuing a credit note; credit-note issuance is out of scope (Decisions log 2026-07-24, Phase 09 review-fix pass).
- **No ACC engine guard.** B9 and the 6th external review #3 rule that ACC-relatedness stays informational, because the RFP itself calls the holder's onward claim "invisible to the billing engine". The prototype raises a review advisory instead.
- **A separate Billing Engine admin surface.** The monitor sits in the Admin Web App; the RFP leaves the placement open and the choice is stated in the monitor's own copy (§11, Phase 09 reading 4).

## Beyond the RFP

- **Money-integrity belts the RFP never asks for.** Billing-time re-check of a funder allocation against the fee under the resolved contract (`allocationStale`), refusal when a pre-invoiced procedure's payer changed (`prepaidCounterpartyChanged`), refusal of a funder split on a pre-invoiced procedure (`prepaidFunderOverride`), and a negative-total belt so no negative invoice is ever raised - `aa-prototype/src/domain/billing/invoiceBuild.ts:298-347` and `:411-420`, all test-pinned in `billingRun.test.ts:455-489`.
- **Per-card failure isolation with resolve-and-retry.** A failed Card yields a `failed` BillingCase and blocks only its own invoice; the List still completes its run, and the monitor's retry rebuilds and then hands off to Xero - `aa-prototype/src/apps/admin/screens/BillingMonitorScreen.tsx:88-99`.
- **Rate snapshotting for reproducibility.** `InvoiceLine` carries no rate field; the rate is written into the line description ("7 units at $35.00 per unit") so a post-hoc master edit cannot change a raised invoice - `aa-prototype/src/domain/billing/invoiceBuild.ts:247-252`, test `billingRun.test.ts:367` (snapshot immunity).
- **Agency framing on the document itself.** Every invoice reads "Billed by Anaesthesia Associates as agent for Dr X", which the RFP implies but never specifies as invoice copy.
- **Visible deduction line for a pre-payment balance** rather than mutating the fee line, so deposit + balance reconciles to the full fee including GST - `aa-prototype/src/domain/billing/invoiceBuild.ts:380-394`, `prePaymentInvoice.test.ts`.
- **Discovery callouts as product surface.** The Xero sim states the NHI-in-Xero contradiction and the mandated duplicate-invoice-number org setting as open AA rulings - screenshot `demo-xero.png`.
- **A protected default-contract invariant** created atomically with each Hospital or direct-billing Insurer and guarded against deletion, end-dating, forward-dating and type or holder changes - `aa-prototype/src/store/contractActions.ts`, tests in `mastersActions.test.ts` and `billingRun.test.ts:445`.
