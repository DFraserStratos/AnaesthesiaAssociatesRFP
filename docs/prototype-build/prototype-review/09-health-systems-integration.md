## Findings

### 09.1 - HL7 messages carry no AIP personnel segments, and routing plus the FHIR Practitioner come from demo metadata  [PARTIAL]
- **RFP says:** "AIP - Appointment personnel: surgeon (ID 12952, Neuro Surgery) and anaesthetist (ID 49641), both BOOKED." (line 1650), listed among "the key segments in this message" (line 1640).
- **Built:** the canned messages are assembled from MSH, SCH, AIS, PID and (for S14) NTE only, `aa-prototype/src/domain/integrations/messages.ts:86-99`. Which List an S12 create lands on comes from a `routing` field on the canned message, not from the wire, `messages.ts:118-127` and `aa-prototype/src/store/integrationActions.ts:145-149`. The Practitioner in the translated FHIR pane is always read from the store as Dr Melanie Souter, `aa-prototype/src/apps/demo/DemoIntegrations.tsx:51-55`, so the locked-target message (whose Card sits on Dr Delaney's Fri 17 List) still renders Souter's HPI in pane 2.
- **Gap:** no AIP or AIL segments exist in the demo corpus, so surgeon and anaesthetist identity, and the hospital and session, are never extracted from a message; the RFP's `~` repeating-field and `&` subcomponent delimiters (line 1605) are also never exercised.
- **Would a workshop audience notice:** possibly. Anyone holding the RFP's own annotated sample beside pane 1 will see two segments missing. The prototype is honest about it in code comments, but nothing on screen says so.
- **Severity:** cosmetic (PROGRESS decision 2026-07-24, Phase 11 message-shape entry item 3, explicitly fences "the AIL/AIP location/personnel segments a real feed carries" out of the demo extractor, so this is a recorded simplification rather than an oversight; the extraction that the demo does claim, patient identity and appointment correlation, is genuinely mapping-driven)

### 09.2 - The internal representation the store consumes is a neutral parsed message, not FHIR  [PARTIAL]
- **RFP says:** "Ideally, the integration engine should operate natively using FHIR R4, with a pre-processing layer responsible for translating inbound HL7 v2 messages into FHIR format before passing them to the core system." (line 1762)
- **Built:** `extractViaMapping` produces a transport-neutral `ParsedMessage` (`aa-prototype/src/domain/integrations/hl7.ts:19-43`) and `extractFromFhir` reads a FHIR bundle back into the same shape (`aa-prototype/src/domain/integrations/fhir.ts:196-232`), so both transports converge on one store effect (`aa-prototype/src/store/integrationActions.ts:237-247`). That is exactly the "FHIR-equivalent internal representation" the RFP's translation paragraph asks for at line 1757.
- **Gap:** for an HL7 feed, the FHIR bundle shown in pane 2 is built for display by `toFhirBundle` and is not the object passed forward; the effect is applied from `ParsedMessage`. The three-pane sequencing (raw, then FHIR, then schedule change) implies the bundle is the pipeline artefact when it is a rendering of it.
- **Would a workshop audience notice:** no. The panes are coherent and the ordering is honest about what changed; only a code reviewer would see that the bundle is not re-consumed.
- **Severity:** cosmetic

### 09.3 - No RESTful FHIR interaction is shown, even in simulated form  [PARTIAL]
- **RFP says:** "the solution must be capable of consuming FHIR Appointment, Patient, and Anaesthetist resources directly via RESTful API" (line 1756), with "Bundle (transaction)" listed among the key resources.
- **Built:** the Southern Cross feed is genuinely FHIR-native (no HL7 pane, typed NHI identifier, NZHIS extension, HPI Practitioner) and is modelled as a `type: 'message'` bundle with a MessageHeader, `aa-prototype/src/domain/integrations/fhir.ts:83-87` and `:116-122`. The simulator subtitle states "All in-browser, no real endpoints", `DemoIntegrations.tsx:115`.
- **Gap:** nothing in the surface expresses REST: no endpoint, verb, search parameter, subscription or transaction-bundle framing, and no `fetch` exists anywhere in the app (PROGRESS convention 4). A technical hospital-integration attendee asking "so how does the FHIR API actually get called, push or poll?" gets only the callout's promise.
- **Would a workshop audience notice:** possibly, in a technical audience; the answer is a talking point rather than a screen.
- **Severity:** cosmetic (REQUIREMENTS §10 fences real HL7 / FHIR endpoints; the missing piece is only a simulated REST framing, not the fenced capability)

### 09.4 - No acknowledgement is returned to the sending hospital system  [MISSING]
- **RFP says:** "respondents must describe their approach to message delivery guarantees, error handling, alerting, and retry logic" (line 1783).
- **Built:** delivery guarantees are demonstrated inbound: store-on-receipt then process (`integrationActions.ts:306-328`), idempotent dedupe by MSH-10, `MAX_ATTEMPTS = 3` with an auto-retry timer, dead-letter, and a manual-intervention queue that loses nothing.
- **Gap:** there is no ACK / NACK (MSA) emitted back to the PAS, and no outbound side of the interface at all. Nothing under `aa-prototype/src` mentions `MSA` or acknowledgement.
- **Would a workshop audience notice:** an HL7-literate attendee might ask; the RFP itself frames this as a narrative ask, and PROGRESS's Phase 11 review-fix entry records that the monitor copy deliberately dropped its earlier "acknowledged per message" claim, so nothing on screen over-claims.
- **Severity:** cosmetic

### 09.5 - The integration message log ships empty, so the reliability surface is blank on a cold open  [PARTIAL]
- **RFP says:** "The solution must provide operational visibility into integration failures" (line 1784).
- **Built:** the Messages tab renders the full log (time, source, event type, control id, appointment id, patient, derived status with attempt count, failure reason, Reprocess) at `aa-prototype/src/apps/admin/screens/IntegrationMonitorScreen.tsx:74-138` over `aa-prototype/src/store/selectors.ts:887-908`, with an attention banner and an amber nav badge.
- **Gap:** the pristine seed contains feeds but no messages, `aa-prototype/src/store/appStore.ts:125-129`. On a fresh load the tab shows only "No messages received yet. Replay one from the integration simulator", the amber badge reads zero, and the four seeded integration-origin Cards have no corresponding log rows. Every reliability story therefore depends on the presenter firing the simulator first.
- **Would a workshop audience notice:** yes if the Integrations tab is opened before any message is replayed, which is a plausible click during free exploration. Within the guided script (S1 and S4 fire messages) it never shows.
- **Severity:** notable

### 09.6 - An S13 to a session the anaesthetist does not hold silently degrades to a time-only edit  [PARTIAL]
- **RFP says:** the system must act on "reschedules" automatically (line 1582) and provide "manual intervention workflows where automated processing cannot proceed" (line 1784).
- **Built:** `aa-prototype/src/store/integrationActions.ts:179-201` looks for a target List with `listForSlot(currentList.anaesthetistId, parsed.scheduledDateISO, session)`; if one is found and differs, the Card is reassigned first and then retimed (a deliberate ordering fix recorded in PROGRESS).
- **Gap:** when no List exists for that anaesthetist on the new date, `target` is `undefined` and control falls through to the same-List branch, which applies only `scheduledTime`. The Card keeps its original day and session, and the monitor reports `processed` rather than parking a manual-intervention item as the unmatched and locked cases do. The date component of the reschedule is discarded without a trace.
- **Would a workshop audience notice:** no. No canned message reaches this path (`MSG-STG-1011` targets Souter's Tue 28 Jul List, which exists), so it is only reachable by editing seed data or the feed mapping.
- **Severity:** cosmetic

## Deliberate exclusions in this section

- **Real HL7 / FHIR endpoints, SFTP, and a real Digital Services Hub / Keycloak connection** - REQUIREMENTS §10. The simulator names all three and labels them referenced, not implemented (`DemoIntegrations.tsx:117-125`).
- **Real OCR / PDF parsing** - REQUIREMENTS §10; the canned rows are the "parse" (`pdfSamples.ts:1-11`).
- **A general-purpose HL7 parser** - REQUIREMENTS §10 and the docblock at `hl7.ts:1-12`: extraction covers exactly the canned SIU segment shapes.
- **AIL / AIP location and personnel extraction, and message-driven routing** - PROGRESS decision 2026-07-24 (Phase 11 message-shape entry, item 3). See finding 09.1.
- **The NHI lookup on the inbound feed path** - REQUIREMENTS I5 scopes the simulated lookup to the ad-hoc / manual card-creation path (per M7); inbound identity is validated and deduped instead.
- **Multi-user concurrency between feeds and apps** - REQUIREMENTS §10 and §11's pure-discovery list: the prototype is single-user and takes an audited last-write-wins stance.

## Beyond the RFP

- **Ethnicity quarantine.** An inbound code outside the NZHIS L4 set never persists: the Card still books, the code is held "pending correction" in both the FHIR extension and the patient record, and a Data quality queue lets the office supply a valid code (`fhir.ts:132-144`, `integrationActions.ts:389-418`, `IntegrationMonitorScreen.tsx:354-397`). The RFP mandates the code set but says nothing about what to do with a bad one.
- **Three-way validator honesty.** `validateEthnicityCode` distinguishes malformed from "well-formed but outside this demo's curated subset", so a real L4 code the demo does not carry is never called invalid (`nzhis.ts:44-78`; visible in `phase11-monitor.png`).
- **Two correlation keys surfaced separately.** MSH-10 dedupes messages, SCH-2 correlates appointments, and the monitor shows both columns (`messages.ts:6-11`, `selectors.ts:887-908`).
- **Operator-facing feed configuration with audit.** The mapping editor is office-only and writes a `feed.update` audit entry, so an onboarding misconfiguration and its fix are both traceable (`integrationActions.ts:348-377`).
- **Dual-format NHI validator widget** inside the integrations surface, covering the Appendix 1 format change and the 1 July 2027 dual-format date (`IntegrationMonitorScreen.tsx:403-429`).
- **PDF facsimile beside the extraction rows,** with one deliberately mistyped NHI and one already-booked row, so read, edit and no-duplicate behaviour are all demonstrable from one document (`pdfSamples.ts`, `IntegrationMonitorScreen.tsx:275-334`).
- **"Start live feed" drip** that streams a whole feed one message per second, which makes the near-real-time claim visible rather than narrated (`DemoIntegrations.tsx:58-72`).
