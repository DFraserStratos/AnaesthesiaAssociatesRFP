The RFP gives two different-looking sets of values for `ListStatus`, and doesn't say which is final:

- p.14 (List entity): *available, available for emergency, unavailable, on leave (etc)*
- p.17 (Supporting/Master Data): *private, public, pre-op, holiday, unavailable, free* — itself marked "(to be confirmed)"

Only "unavailable" appears in both. Need AA to confirm: is one of these the real list and the other
stale, do they merge into one combined vocabulary, or are they actually two separate fields that got
listed under the same "List Status" heading (see OQ-27, which is about that split)? Also need the
colour assigned to each final value, per RFP's "description, colour" field pair.

## Answer

As you would have heard in the transcript.

The System will create AM & PM slots for every active anaesthetist. These slots can have a status, or a list.

From the transcript, as a working model still to be made clear (Greg: "I think we need to be clear about what the logical model is, and I don't think we are"): on each new day of the four-month rolling horizon the system creates an AM and a PM slot for every active anaesthetist, and a slot is free by default (Greg's "Isn't that the default?", which Donald took up). A slot holds a status (for example free, on holiday, or unavailable) until a List is put in it; Donald pictures the List then overriding the status ("something to that effect"; he left the mechanics to the development team). So there are three things:

- an empty slot, which has a status
- a List, which has content
- a Draft List, a List with no anaesthetist

The availability values belong to the slot, not to the List. A List takes its status from its anaesthetist, and a List with no anaesthetist is unassigned. Slots exist even when free or unavailable, so the views can show every anaesthetist. Not named yet: the final list of status values and the colour for each.
