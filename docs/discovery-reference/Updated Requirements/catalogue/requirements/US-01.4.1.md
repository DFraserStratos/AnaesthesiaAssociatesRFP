An admin can reassign a List, together with all its bookings, to another anaesthetist.

The List's bookings, status history and [audit trail](US-13.5.2) all carry over intact: nothing is re-keyed and no history is lost.

## Technical discussion

Proposed in our RFP response (answer to the RFP's Open Question 2, see OQ-08):

- Manual re-keying of Bookings for illness cover is avoided, because it loses the Bookings' audit history.
- The owning anaesthetist is a reference held on the List aggregate, the root to which its Bookings, statuses, attachments and history are anchored. Reassignment changes that owner reference, so the whole List moves intact with its full change history.
- The move is captured as a single temporal-table event (from, to, by, when) that adds to history without rewriting it.
- [Two-slots-per-day invariant](US-01.1.1): the swap consumes the covering anaesthetist's existing half-day Slot rather than adding a third List, and the vacated Slot returns to available (or is marked unavailable if more appropriate), so the calendar has no gaps or duplicates.

## Notes

Mechanism answered in the technical discussion (OQ-08): change the owner reference on the List.
