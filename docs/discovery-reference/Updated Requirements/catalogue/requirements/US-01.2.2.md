Admins maintain the Slot availability status table (the RFP's ListStatus) directly. The statuses are a user-maintained list, not a fixed set in code: each status has a fixed internal ID, an editable label and an editable colour. Any rule that depends on a status reads its ID, not its label.

This means statuses can be added or renamed without any code changes, and a new customer can have different statuses (Greg: "much better than an enum").

This is the availability status, not the DRAFT, SUBMITTED and AUTHORISED [approval state](EP-07).

## Acceptance criteria

- Given an admin renames a status or changes its colour, when it is saved, then every view shows the new label and colour, and rules that use the status behave as before.
- Given an admin adds a status, then it can be used without a code change.

## Notes

The OQ-17 answer settled that availability values belong to the Slot, not to the List, and that a List takes its status from its anaesthetist (a List with no anaesthetist is unassigned). The starting values are as in [half-day availability](US-01.2.1). The final values, and which of today's are redundant, are to be defined with Vanessa and AA's users. Greg: it "will need some implementation thinking".

Greg endorsed statuses as master data, recalling an ERP whose statuses were an enum: it "caused horrendous problems" and needed a rewrite.
