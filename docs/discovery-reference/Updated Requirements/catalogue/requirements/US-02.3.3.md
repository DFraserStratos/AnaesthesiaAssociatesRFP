After an admin [saves a change to a Booking](US-02.3.2), or reassigns a List to another anaesthetist, the system opens a compose window in their default mail client, built from the saved changes and prefilled with:

- a subject
- a boilerplate message
- the list of changes (those since the last save, or those remembered since the last email: OQ-69)
- the To address, where known: the hospital contact for a cover change (a new anaesthetist on a List), the surgeon's room for a change to a Booking

The admin reviews and edits it, including the To address, and sends it themselves. The system sends nothing.

This is so hospitals and admin teams are told about a change without a true integration and without writing each email by hand. The main trigger is a cover change (a new anaesthetist on a List), which Vanessa spends a lot of time emailing today.

## Acceptance criteria

- **Compose window.** Given a saved change to a Booking or a List reassignment, when the email is offered and the admin accepts it, then the default mail client opens with the subject, boilerplate and change list filled in.
- **To address.** Given a cover change, then the hospital contact email is in the To field; given a change to a Booking, then the surgeon's room contact email is. Where no contact email is held, To is left empty, and the admin can edit it either way.
- **Length.** Given the change list is too long for the limit, then the body is shortened to fit and says so.
- **Nothing sent.** The system does not send the email or record it as sent.

## Technical discussion

This uses a `mailto:` link. Limits to design around: plain text only (no formatting, no attachments), and a practical length of roughly 2,000 characters for the whole link, which varies by mail client. The To address needs contact emails held on the hospital record ([reference tables](US-13.4.1)) and on the [surgeons' room](US-13.6.1).
