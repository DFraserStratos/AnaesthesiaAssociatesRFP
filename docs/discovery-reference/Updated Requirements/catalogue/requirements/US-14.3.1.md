The system acts on each inbound message as soon as it is received, rather than waiting for a batch.

This is so a late booking can still reach the schedule [right up until the operating session starts](US-02.5.4).

## Technical discussion

Proposed in our RFP response: latency is likely caused by batching rather than SFTP itself. The system would poll the existing drop at short intervals and process each message the moment it lands, bringing latency from hours to under a minute without any hospital changing anything. The response prefers going live on near-real-time processing immediately, with hospitals moving to push transports progressively, rather than go-live waiting on other organisations.

The response assumes an existing SFTP drop of hospital messages. Q&A 2026-09-24 #4 said no live hospital integration exists today, which the meeting of 2026-09-29 corrected: the current system has integrations with St George's and Southern Cross (Notes 2026-09-29 #14).
