The system represents inbound bookings internally as FHIR R4 resources.

Where a hospital sends HL7 v2 rather than FHIR, the system translates the HL7 v2 message into that same FHIR R4 form, so the system works from one consistent internal representation no matter which format a hospital sends.

## Technical discussion

Proposed in our RFP response, as a change to the RFP: all messages are translated to Stratos's own internal data model (canonical booking, patient and practitioner data), not to a messaging format. Translators are written from each source format (HL7 v2, FHIR) into that model, and the scheduling core, validation and audit never see HL7 or FHIR. This avoids a double-hop of translating to FHIR and then translating again; a messaging format is for transport, the data model is what rules are checked against.

This differs from the story as written, which represents bookings internally as FHIR R4 resources.
