A Procedure's price follows its Contract. The system takes the first of these that applies:

1. an [office price override](US-05.4.2) at review
2. a price [the anaesthetist typed](US-05.4.1), on No contract (RVG) and first-party Contracts only
3. the Contract's fixed price
4. BTM units multiplied by the Contract's fixed rate if it has one, otherwise by [the anaesthetist's own unit value](US-12.1.1), less any discount: the Contract's [fixed discount](US-05.4.3), or the anaesthetist's own

A price of 0 gives a no-charge invoice, and BTM is still recorded.

This is so every Procedure is priced the same way whichever Contract it is on, and the units behind the price are never lost.

## Technical discussion

The draft technical design ([AR-29 p7](AR-29#p7)) prices each Procedure on its own when the List is authorised:

- **Resolver.** For each value it looks down through the selected Contract's line for the procedure, then the procedure, then the RVG group; the first value found wins. Blank means look through to the next layer; a value, including 0, stops it. Only a Contract valid on the procedure date is used. The resolved values and the layer each came from go into the pricing snapshot.
- **Validation.** The engine rejects the Procedure, rather than ignoring an input, when a price or discount is entered on a Contract that does not allow it, when BTM units are missing and no fixed price resolves, or when the Contract is not valid on the procedure date.
- **Precedence.** Office override, then the anaesthetist's typed price, then the fixed price, then calculated: (B + T + M) x rate x (1 - discount / 100), with the source of the price recorded.

The design predates the directors' answers: its calculated step has a term for the anaesthetist's discount but none for a Contract's fixed discount, and it keeps the Contract rate dormant. Both now need logic. The design is a draft and may change before the catch-up build.
