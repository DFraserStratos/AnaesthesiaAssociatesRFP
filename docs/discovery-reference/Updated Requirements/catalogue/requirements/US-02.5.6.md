The Scheduling Engine handles the same Booking being edited by two sources close together in time, for example an automated update from an integration arriving while an admin or the anaesthetist is editing it.

Neither change is ever lost silently.

## Technical discussion

Proposed in our RFP response (answer to the RFP's Open Question 1, see OQ-07): optimistic concurrency, not locking. Bookings and Procedures are editable concurrently from hospital messages, the anaesthetist app and the admin web app up to the day of the procedure; every source edits freely and conflicts are caught at save. Locking was rejected for a worse user experience and the risk of records being left locked.

- Row-version backstop in Azure SQL: each Booking and Procedure carries a row version, read with the data and checked on update, so silent data loss is impossible even for simultaneous edits.
- Resolved in the domain first: non-conflicting edits (different fields) are merged and both kept; only genuine same-field contention is escalated to a person as a clear, actionable message, and a raw database rejection never reaches a user as a technical error.
- Which fields may auto-apply and which must stop for a person is a business policy, to be mapped field-by-field with AA in discovery.

## Notes

Mechanism answered in the technical discussion (OQ-07): optimistic concurrency with a row-version backstop. The field-by-field auto-apply policy is still to be mapped with AA.

Future Work (2026-10-02): Donald put it out of scope for now "because this is related to an automated thing". Until automated updates arrive, Booking changes come from people, through the admin's explicit [save](US-02.3.2) and the anaesthetist's app.
