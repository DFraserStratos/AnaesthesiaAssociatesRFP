A dedicated Xero organisation provides AA with accounts receivable and banking, sitting underneath the Billing/Invoice Engine rather than replacing it as the [system of record](US-08.3.2).

For every [ledger pair](US-08.3.1), the engine mirrors an ACCREC and a draft ACCPAY into Xero, detects when each is paid by webhook plus a daily poll, and manages Xero contacts using a hidden internal ID, so the patient's [NHI never reaches Xero](US-15.0.6).

## Technical discussion

Proposed in our RFP response: Xero integrations are built to be resilient by design, with the billing engine as the system of record.

- Asynchronous processing: Xero calls are handled outside the main application request cycle, so a slow or unavailable Xero API does not affect the user experience or block workflow progression unless necessary.
- Durable queue: every financial event is written to a queue before it is sent to Xero. A failed call retries automatically with exponential backoff, so nothing is lost.
- Idempotency: each transaction carries a unique reference, so retries never result in duplicate invoices.
- Divergence between the engine and Xero: the same financial event exists in two places and the two can drift apart. Anticipated cases include an invoice voided or amended directly in Xero by AA staff, which is invisible to the engine unless something is looking for it, and a payment recorded against an invoice the engine has since credited, where the order events land in matters. The right answer to each is as much an accounting and operational decision as a technical one, to be worked through with AA in Scoping and Design.
- Testing: end-to-end testing emphasises the Xero interface, with explicit coverage of failure and recovery scenarios (message delivery, error handling, retry and alerting).
