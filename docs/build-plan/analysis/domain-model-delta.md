## DM-11 · The arriving List is what the office decides

**Kind:** NewEntity (a derived grouping with a stored List-level decision) · **Size:** L · **Must precede:** DM-12, DM-13, DM-17, DM-19 · **Status:** open, new at `8637b65`

**Catalogue:** [US-02.1.2](../../../requirements-board/requirements/stories/US-02.1.2.md) (decide a whole List; leave one Booking's change out; place, add to, make a Draft List or reject), [US-02.1.4](../../../requirements-board/requirements/stories/US-02.1.4.md) (one feed grouped by List; a file is a heading over its Lists, a PDF is one List; filters By source, Needs NHI, Decided), [US-02.1.6](../../../requirements-board/requirements/stories/US-02.1.6.md) (unchanged Lists confirmed together), [US-01.6.1](../../../requirements-board/requirements/stories/US-01.6.1.md), [US-01.3.3](../../../requirements-board/requirements/stories/US-01.3.3.md); `domain-model.md` "Matching screen". Note #1, #2, #9, #10, #12.

**Prototype:** the unit is a row. An `ImportBatch` is a file or message and holds `rowIds` (`aa-prototype/src/domain/types.ts:2915`); each `ImportRow` has its own `status` (`open | applied | rejected`) and one `ImportDecision` (`types.ts:2876`: `match`, `createBooking`, `createList`, `createDraft`, `reject`), made by `decideImportRow` (`aa-prototype/src/store/matchingActions.ts:699`) one row at a time. The matcher assesses rows (`suggestDecision`, `aa-prototype/src/domain/intake/matching.ts:503`; `matchingQueue` returns per-row assessments and counts of rows, `:647`); a List appears only as `RowAssessment.targetListId`. Placing a new List creates it from the first row and the others are separate `createBooking` decisions onto it. An unchanged row (`changeType: 'noChange'`) is its own decision ("Mark as matched, nothing to change", `matching.ts:614`). There is no way to leave one change out except to leave the row open, and nothing confirms several unchanged rows at once.

**Impact:** an "arriving List" is derived, never stored: the rows of one arrival that share hospital, day, session and surgeon (a PDF is one; a hospital file is several under a heading). The office's decision on it is one change set that applies the ticked rows' changes and records each row decided. Needs: (1) a row outcome for "left out" that is decided but changed nothing (today the union has no member for it; without one a left-out row hangs in the feed and "Decided" cannot find it). `reject` already decides a row and changes nothing (`types.ts:2876`), so the cheapest shape is a reject carrying a fixed "left out" reason; a member of its own (`leaveOut`) reads better in the Decided filter and the audit, and keeps "rejected" for wrong rows, so `ImportDecision` gains it (the phase's call); (2) a **List-level place action** that creates the List in one Slot and puts every row's Booking on it (today's first-row-then-rest sequence is the building block); reject of a whole List is a reject of each row with one reason; (3) a **confirm unchanged** action over all `noChange` Lists of an arrival, which must stay a person's act (never run by the arrival); (4) the counts and the stats strip move from rows to Lists; Intake's attention count still counts each waiting-for-NHI row once ([US-11.1.5](../../../requirements-board/requirements/stories/US-11.1.5.md)), so its unit needs one stated rule. The surgeon is a List attribute but today a per-row correction (`ImportRowCorrections.surgeonId`), and a row whose surgeon is not recognised has no List key to group by: the arriving List groups by the surgeon as sent, and choosing the surgeon once for the List is part of the List-level place action. The rows, their audit entries and the stub settling (`settleStubForRow`, inside the decision's commit) stay; the new work is the wrapper and the one new outcome. An unchanged List only exists in the feed if identical re-arrivals are not skipped at staging: that is DM-21. A new `ImportDecision` member changes the persisted intake slice's content, so it bumps `PERSIST_VERSION` (80 to the next) only if the seed carries decided rows; an optional member alone does not. Both DM-11 and DM-15 rewrite `matchingActions.ts` and the matching screens: one lane.

**Verified:** corrected. The catalogue claims hold (US-02.1.2 "A whole List", US-02.1.4 "Grouped by List", US-02.1.6). The prototype claims hold: no group, leave-out or confirm-all exists, and the Decided filter exists today but over rows (`MatchingScreen.tsx:99`, `FilterPills` open, unmatched, decided). Corrected: "needs one new outcome" overstated a necessity (reject can carry it), and the surgeon's List-level role was missing.

## DM-12 · A List keeps its versions, and a match shows its keys

**Kind:** ChangedRelationship (a derived read, with one stored link) · **Size:** M · **Needs:** DM-11 · **Status:** open, new at `8637b65`

**Catalogue:** [US-02.1.3](../../../requirements-board/requirements/stories/US-02.1.3.md) (each match key and whether it agreed, how many patients were found by NHI, the List's earlier versions, its Slot; a hospital List for the same surgeon, hospital, day and session is an update to the rooms' List, not a new one), [US-02.2.1](../../../requirements-board/requirements/stories/US-02.2.1.md) (a re-sent List merged as the next version), [US-02.2.4](../../../requirements-board/requirements/stories/US-02.2.4.md). Note #3, #4, #8.

**Prototype:** a List remembers only where it first came from (`ListOrigin`, `aa-prototype/src/domain/types.ts:844`). The matcher's output is one `MatchBasis` per Booking (`listAndPatient`, `patientOnDay`, `byHand`, `matching.ts:218`), with no record of which keys agreed and no count of patients found by NHI. The only version link is PDF to PDF: `SurgeonPdfList.replacesId` ("our reading", `types.ts:2972`, `resentPdfListOf` at `aa-prototype/src/domain/intake/pdfLists.ts:274`). A hospital row for a rooms-created List matches Booking by Booking (so a changed time shows as a modification and a new patient as a Booking to create on that List), but nothing says "this is the same List's second version", and the List's earlier arrivals are not listed anywhere.

**Impact:** two pure reads. `matchKeys(arrivingList)` gives surgeon, hospital and day and session each agreed or not, and the number of its patients found by NHI among the List's Bookings (no score). `listVersions(state, listId)` gives the first version (the List's origin and its arrival) and each later arrival that resolved to it, from either source, so a hospital arrival after a rooms PDF reads as an update. The versions come from decided rows (`decision.match.bookingId`, `createBooking.listId`, `createList.listId`) plus open rows targeting the List. One stored gap: a `match` decision names a Booking, not a List (`types.ts:2877`), and a Booking can later move to another List (`reassignBooking`), so version history read from Bookings would misplace an arrival; recording the `listId` on a `match` decision (optional field, no bump) closes it. The hospital and rooms rows must also agree on the surgeon key: `resolveSurgeon` already handles a name or HPI. No new stored entity.

**Verified:** upheld. `findMatch` already looks up the List by hospital, day, session and surgeon, then the patient by NHI (`aa-prototype/src/domain/intake/matching.ts:259`, basis `listAndPatient`), so the keys exist in the matcher and only their per-key result and the NHI count are not exposed; a hospital row for a rooms-made List already matches at that key regardless of the List's origin, so the "update to the same List" behaviour is most of the way there at row level.

## DM-15 · Rows arrive by source, not by an office import

**Kind:** ChangedLifecycle · **Size:** L · **Must precede:** DM-14 · **Status:** open, new at `8637b65`

**Catalogue:** [US-02.1.1](../../../requirements-board/requirements/stories/US-02.1.1.md) (no import step), [US-02.1.5](../../../requirements-board/requirements/stories/US-02.1.5.md) (arrives by itself; nothing applied silently; inbound only), [US-02.2.1](../../../requirements-board/requirements/stories/US-02.2.1.md) (PDFs read from the office's mailbox as they arrive; added by hand as the fallback, with the sender), [US-02.2.4](../../../requirements-board/requirements/stories/US-02.2.4.md), `domain-model.md` "Sources". Note #5, #6. Replaces the 18 November answer to [OQ-109](../../../requirements-board/requirements/questions/OQ-109.md).

**Prototype:** every arrival starts with an office act. `importHospitalDownload` is office-only and stamps `ImportBatch.importedBy` with the person (`aa-prototype/src/store/matchingActions.ts:176,213`; the button is "Import hospital file", `aa-prototype/src/apps/admin/screens/MatchingScreen.tsx:67,122`; the channel doc reads "imported through an integration", `types.ts:2812`). A PDF goes through two office steps: `uploadPdfList` (office types the sender and picks a sample, `aa-prototype/src/store/pdfListActions.ts:93`, `receivedBy`) puts a `SurgeonPdfList` at status `received` on its own PDF lists tab (`aa-prototype/src/apps/admin/routes.tsx:370`), and `sendPdfListToMatching` (`pdfListActions.ts:191`) stages its rows. The channel `manualSheet` is a daily sheet the office keys; no catalogue source matches it. No arrival exists that produced no rows (a batch is made only when `fresh.length > 0`, `matchingActions.ts:138`), so an unreadable or fully duplicate message leaves no trace. The demo triggers drive the same office actions: arrival-shaped ones already exist ("hospital sends its list", `receiveTheatreList` at `aa-prototype/src/store/matchingDemo.ts:71`, and `receiveResentPdfList`, registered at `aa-prototype/src/shared/demoTriggers/registry.ts:2365` and `:1209`) but run as the office actor, and the Forte Health sheet trigger calls `importHospitalDownload` (`registry.ts:2464`). The PWA's office stand-in stages `manualSheet` rows too (`aa-prototype/src/store/officeStandIn.ts:350`).

**Impact:** an arrival is a record made by a **source actor** (`actor.source === 'integration'` already exists), carries which source sent it and when, and exists even when it yields no rows (DM-14 and DM-16 read it for "held"). `ImportBatch.importedBy` (a person) becomes the source, with the person kept only for a PDF added by hand (the fallback, with its typed sender). The two-step PDF (`received` then `sent`) collapses: a PDF's rows land on the matching screen on arrival, and the office's correction before ingest is the row correction that exists (`ImportRowCorrections`, with `PdfRowCorrection` history), so the `SurgeonPdfList` slice either becomes the PDF attachment of the arrival or folds into it (the phase's choice; the PDF itself and its reading stay, DM-16). One loss to avoid: `PdfRowField` lets the office correct the ethnicity code before sending (`aa-prototype/src/store/pdfListActions.ts:147`) but `ImportRowCorrections` has no ethnicity (`types.ts:2853`), and `PdfRowCorrection` keeps from, to, who and when per change; the row correction must take both. The office actions `importHospitalDownload`, `uploadPdfList` (as a primary route) and `sendPdfListToMatching` go; the hospital and mailbox arrivals are `DemoTrigger` entries on the matching screen's own page ("St George's sends its list", "A rooms' PDF reaches the mailbox"), per the simulated-events rule. `manualSheet` is the phase's call: keep as a demo-only arrival (the no-NHI sample and the PWA stand-in use it) or drop it and move them to `download`. Nothing is applied by an arrival: the stub placement for rows with no NHI (`placeStubsForRows`) does happen on arrival, as today. Persisted intake slice changes shape: bump `PERSIST_VERSION`.
