How a phase runs
  1. Phases come from requirement changes. Record them with /update-requirements, commit, then run /update-build-plan: it grades only what changed and appends phases here. Routine fixes and polish use the app-change skill instead.
  2. Pick the next phase from the table below, respecting the order in "Sequencing and rules".
  3. Open a fresh Claude Code session and paste that phase's kick-off prompt. It loads the run-build-phase skill, which reads a context pack and the phase doc before touching anything.
  4. Drift check first. Each session diffs its items against 8637b65, reports what changed, and adapts the plan before building.
  5. The agent plans, builds and tests itself without waiting for approval (ROADMAP.md "Owner review: agents test themselves").
  6. Every phase ends the same way: npm run build, npm run build:pwa, npx vitest run, the board check and (for UI work) npm run shots green; the checklist run item by item; the adversarial review-and-fix pass; (screenshots and the demo guide wait for the owner's sweep); a PROGRESS.md entry; a commit when green (never a push).
  7. Then the owner tests. Screenshots, capture recipes and the demo guide are brought in step later, in one sweep the owner triggers (/sweep), not per phase.

Demo buttons live on their screens. Anything that cannot be shown through normal use gets a trigger in the harness bar's "Demo actions" menu, listed only on the screen where it matters, and the installed PWA gets the same in its Demo sheet. The mechanism exists (src/shared/demoTriggers): phases register into it.

The demo guide and screenshots are deliverables. A version of each goes to Anaesthesia Associates, so every phase leaves them matching the app for exactly what it changed, and the screenshots are captured only after the owner approves the phase.
