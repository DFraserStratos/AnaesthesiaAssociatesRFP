Making the Review table easy to check

The Review table is where the office checks a List before authorising it, so it should be quick to scan. Today it isn't. One part is a plain bug and the rest is about how the Procedures cell is laid out. Below: what's wrong, three ways to fix it, all shown with the same Forte Health AM list, and how to make the row match the Day view's bookings list.

Recommendation: option B, procedure lines. Each Procedure gets its own line across the table, with its own code, units and fee, so the units add up where you can see them. The payer and Change appear once per Booking, not once per Procedure.

Fix the blank corner first in any case: the Totals row has one cell too many. It's a one-line fix.

What's wrong today

The letters match the marks on the Today table above.

  • A

    A phantom column

    The Totals row has ten cells for nine headings (an extra empty <Td /> after the colSpan={4}). The table grows a tenth column with no heading, which is the blank white corner. It also moves the totals one column right: 31 sits under Fee and $636.00 under Flags.

  • B

    Everything looks the same

    Each Procedure is six lines at 12 to 12.5px in grey, and the surgeon's text is in quoted monospace, which reads like code. Nothing stands out, so you have to read every line.

  • C

    The same thing three times

    "Patient pays · Change · Email" repeats for every Procedure, and Billed to already says Graeme Tullett. "RVG" is in the Contract line twice. The $0.00 typed price is shown three times: on the Contract line, as a pill and in the Fee cell.

  • D

    The useful part gets cut off

    The Procedures column stops at 300px, so the RVG description, which is how you check the code, is cut off with an ellipsis. Meanwhile Times and B · T · M take up width with one short line each.

  • E

    Units are split across the row

    "Primary · B + T + M 3 of 7" is in the Procedures cell, "6 · 6 · 7 / M 7 · split 3 · 2 · 2" in B · T · M and 24 in Units. You can't see that the umbilical hernia earned 5 units without doing the sums yourself.

  • F

    Actions in the Flags column

    History and Open sit in the Flags column, so every row looks flagged at a glance. Flags tied to one Procedure sit inside the Procedures cell instead, away from the column named for them.

One way to show a Booking on both screens

The Day view's bookings list already does this well: time, patient, procedure, Contract, code chip, from strongest to quietest. The Review table should use the same parts, styled the same way, and add only the columns it needs for checking (times, units, fee, flags).

Recommendation

Option B, in this order. Step 1 stands alone and could go in today.

What changes

  1. Remove the extra Totals cell. The totals line up under Units and Fee, and the blank corner goes.
  2. One table row per Procedure. Each Booking is its own <tbody>, with Time and the patient cell spanning its rows, so a light rule groups the Booking and hover lights it up as one.
  3. A Procedure line in the Day view's style: code chip, the procedure text in 13.5 / 500 ink, the RVG description in full underneath, then the Contract in mist.
  4. Numbers per Procedure: its own times, B · T · M, units and fee. A dashed subtotal row adds them up and names the modifier split once ("Modifiers 7, split 3 · 2 · 2").
  5. Payer once: "Patient pays" with the email and Change goes under the patient. It moves onto the Procedure line only when the Procedures' payers differ. The Billed to column goes.
  6. Flags on the line they belong to, with Approve and Correct next to the pill. History and Open get their own last column. A typed price shows once in Fee and once as a flag.

Why B over A and C

  • A is the cheapest and reads better, but leaves the units maths split across three columns. With three Procedures the cell is still a tall block next to empty space.
  • C matches the Day drawer most closely, but Review is for checking: hiding the Contract and units behind a click means opening every row on a 30-Booking List. It suits a summary page better than a checking page.
  • B keeps everything on screen, puts each Procedure's numbers on one line, and is no taller than today because the repeated payer lines go.

Where it lives in the code

  • ReviewScreen.tsx: the row becomes a <tbody> per Booking, the Totals row loses a cell, and the Billed to and flag placement changes.
  • ProcedureStack compact density, or a new line density, so the List drawer rows and Review share one Procedure line rather than each keeping its own.
  • Per-Procedure units and fee already come from bookingFee (totals.views[id].allocation and .fee). Nothing new in billing.
