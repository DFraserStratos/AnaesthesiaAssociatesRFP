Profiles that show the person's usual week

Recurring bookings live in one place today: Master data › Recurring bookings, a single table of every standing arrangement in the practice. That list is useful for the office's overview. But the question asked most is about one person: "what does Dr Souter usually do on a Tuesday?" or "who covers Ms Patel's Wednesday afternoons?" This page draws five ways to put each person's recurring bookings on their own profile, and to tidy the profiles while we're there. Every idea has an anaesthetist view (Dr Melanie Souter) and a surgeon view (Ms K. Patel), drawn from the seed.

What the catalogue says a profile holds

Anaesthetist

  • Identity: name, registration number (the key), HPI CPN (mandatory)
  • Contact: phone and email
  • Bank account (mandatory) and GST number
  • Rate per unit and priority tier (tier is office only)
  • Status: start date, last day, reason

Why recurring bookings belong on the profile

They're a standing arrangement between two people

A recurring booking pairs a hospital, an anaesthetist, a surgeon, a weekday and a session (US-01.3.2), and drives about 80% of the Lists. So it belongs to both profiles. The anaesthetist's page shows the surgeon, and the surgeon's page shows the anaesthetist.

The catalogue left "edit from both ends" open

US-01.3.2's note says the surgeon and the anaesthetist each keep their own arrangements, and that editing one from either end is unsettled. A section on each profile that opens the same Add and Edit sheet, with that person already filled in, settles it without a second record.

The "Next Lists" panel only shows what's already made

Next Lists shows the three Lists from today. It doesn't say which are regular and which are one-offs, or what the person's week looks like after the canvas horizon.

Things to keep in mind

Public sessions are not recurring bookings: they are a weekly Public series on the anaesthetist's availability (since Phase 32d). Some ideas show them in the week, greyed and marked as availability. Retired recurring bookings stay for history and never project.

The five ideas

Each mock marks the new recurring bookings section with a teal NEW tag. The tag is only a review aid here; it isn't part of the design.

AOne more panel section

Keep today's page as it is and add "Recurring bookings" to the side panel, between Pairings and Contracts, in the same three rows and See all as its neighbours. Add opens today's sheet with the person filled in.

For

  • The smallest change: one more RailSection, the pattern the Contracts and Next Lists sections already use.
  • Nothing about the cards moves, so the demo guide and screenshots barely change.

Against

  • Three rows of a 320px panel is cramped for an arrangement with five facts.
  • The week can't be seen at a glance; a full-time anaesthetist has six or more rows behind See all.
  • The page itself doesn't look any better.
Build size

BTidied cards and a recurring bookings table

Merge the small cards so the main column reads as one profile: Identity and Contact become one Details card, and the money cards sit side by side. Recurring bookings then get a full-width card, with a table, Edit and Retire as text actions, and retired rows behind a toggle.

For

  • The table has the same columns as Master data's list, so it reads the same in both places.
  • Fewer, larger cards: the page reads as a profile, not six forms.
  • Every action is in the row, as on Draft Lists.

Against

  • A table still doesn't show the week's shape (gaps, double days).
  • Merging cards changes what one Save covers (two cards become one edit).
Build size

CThe usual week first

A new header (initials, name, and a strip of key facts that holds the status and HPI CPN) sits over a Monday to Friday, AM and PM grid of the person's recurring bookings: the usual week. Clicking a block opens the Edit sheet, and an empty half-day opens Add for that day. The detail cards move below; a surgeon's Specialties get their own card, edited as removable chips.

For

  • Answers "what does their week look like" in one look, for both kinds of person.
  • On a surgeon, the grid shows who covers each session; two anaesthetists in one session stack in the cell.
  • The anaesthetist's grid can show Public sessions, greyed, so free half-days are really free.
  • The fact strip leads with Status (a green dot, or "Inactive from" or "Retired" in its place) and the HPI CPN, then what the office checks most: rate and tier, or specialties and practice.
  • Specialties use the app's existing chip picker (ChipMultiSelect): pick from AA's list to add one, × to remove, at least one kept. "Editing specialties" shows Ms Patel with a second one, Gastroenterology, just added.

Still to confirm with AA

Whether a surgeon can hold more than one specialty (US-13.6.6 allows it; Ben said "No" on 5 Nov). If AA says one only, the same card holds a single select instead of chips.

Against

  • A new component: no week grid like it exists in Admin (the DayGrid is a day of the whole practice).
  • Weekend sessions and start or end dates don't fit the grid; they need a note or a list view.
  • Details sit below the fold on a laptop.
Build size

DTabs

The same new header, then tabs: Details, Recurring bookings, Lists, Contracts, Pairings, History. Each section gets a full-width page, so the recurring bookings tab can carry filters and a summary line. Shown here with the Recurring bookings tab open.

For

  • Room to grow: Lists, Contracts and History each get a full table instead of three rows.
  • Each tab is short; nothing scrolls on a laptop.
  • Tabs are a pattern Admin already uses (People, Lists, Finances).

Against

  • No single screen shows the whole person; the office clicks between tabs.
  • Undoes the record pattern (cards plus side panel) that Contracts and Parties share.
  • The most rework of the screenshots and demo guide.
Build size

ESchedule first, details compact

The main column becomes "Schedule": each recurring booking on a row with its next four dates, where any date that won't run as usual is coloured (surgeon changed, sent to a Draft List). All the profile fields fold into one compact Details card in the side panel, each section with its own Edit.

For

  • Shows the recurring booking and what it actually made, so exceptions are visible before the day.
  • Merges "Next Lists" into the schedule: one place for the person's sessions.
  • Details stay one click from editing, in less space.

Against

  • Puts the schedule ahead of identity and bank details, which the office edits less but must find fast.
  • Working out each date's status reads the projection and the Lists: new domain code.
  • A narrow Details card is tight for bank details and contacts.
Build size

Decide

My pick: C, the usual week first

The grid answers the question the office actually asks, for both kinds of person, and it's the only idea where the page looks clearly better than today. It keeps the record pattern: cards below, side panel on the right.

From B, I'd borrow the table as a "List" toggle on the same card (for weekend sessions, start and end dates and retired rows). From E, the coloured exception dates could come later, as a second step.
