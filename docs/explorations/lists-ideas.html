One place for the work Lists still need

Draft Lists, Conflicts and the Review queue are three nav entries, three badges and three slightly different pages. People, Contracts and Finances each pulled scattered pages into one section with tabs. This page draws five ways of doing the same for Lists, on this morning's seeded data (demo day Tuesday 24 November), so you can compare them a screen at a time.

Nothing here gets built until Intake's rebuild is finished. Intake's uncommitted work touches the same nav and routes this would.

What the research found

You've asked for it twice

The Finances note: "I might make a more unified lists page in the future." The Contracts-to-set note: draft Lists, conflicts, the review queue, and maybe Lists without Contracts. The catalogue records it as an idea, not a decision.

Two kinds of work, one office

Draft Lists, conflicts and Contracts to set are done before the day. Authorising is done after it, once the anaesthetist submits. The same office role does all of it, and every row is a List.

The pages are uneven

Draft Lists (47) and the Review queue (10) have no search, filters or paging. Conflicts is down to hospital closures only, about six rows: too thin for a nav entry of its own.

Review is half billing

The Review queue's Lists tab is the List's last step. Its Events tab approves credits and pre-op events, which aren't Lists at all and sit better beside Payments' "Events awaiting the run".

Intake isn't in the way

Intake ends once an arrival is placed or applied. It can make a Draft List, but four of the five ways a Draft List starts have nothing to do with Intake, and conflicts never touch it.

The Day view keeps its part

US-01.6.2 wants Draft Lists in the day view as well as on their own page. The band and drawers stay either way; this section is the all-dates view.

The badge is the hard part

Added up, the four queues come to 75. A Draft List at a closed hospital counts once, so 74. A number that size stops meaning "act now".

Finances counts only what needs doing and hides a tab's count at zero. People and Contracts count what each tab lists. The Decide page asks which rule Lists follows.

The five ideas

AFour tabs, one per job

The Finances pattern applied to Lists: one nav entry, a routed tab for each kind of work, each with its own table and filters. Review's Events move to Finances.

For

  • Works exactly like People, Contracts and Finances: nothing new to learn.
  • Each tab keeps the columns and actions its job needs (a Draft List's origin, a List's Contract progress, when it was submitted).
  • Each old page becomes one tab, so old links redirect cleanly.
  • A List's review page nests under To authorise, with Back to the queue.

Against

  • A Draft List at a closed hospital shows on two tabs.
  • Work before the day and sign-off after it sit side by side.
  • The section badge is large unless it counts only part of the work.

What moves

  • Draft Lists, Conflicts and Review queue become one nav entry.
  • Contracts to set gets a tab here and stays on the Day rail.
  • Review's Events tab joins Finances › Payments.
  • Draft Lists and To authorise gain search, filters and paging.
Build size

BOne worklist

Every List that needs something, once, soonest first, with what it needs in its own column. Filter pills stand in for tabs. A List with two problems is one row.

For

  • Each List shows once with everything it needs, so the overlap goes away and the badge is an honest count of Lists.
  • Soonest first is the order the office works in.
  • The pills give each job its own view without a tab strip.

Against

  • The action changes row by row (Assign, Reassign, Set Contracts, Review).
  • Shared columns mean each job loses some detail: no origin, no submitted time, no Contract progress.
  • Lists to authorise are mostly in the past, so they crowd the top of a soonest-first list.
  • Breaks from the three sections' tab pattern.

What moves

  • The same three nav entries become one.
  • A new read model merges four sources into one row per List.
Build size

CDay by day

Pick a day on the left and see what its Lists still need before it's ready. Lists waiting to be authorised sit above the days as their own entry.

For

  • Matches how the office works: tomorrow first, then the rest of the week.
  • Each day says when it's ready ("38 other Lists are ready"), which none of the other ideas can.
  • Hands off to the Day view for that date in one click.

Against

  • A second day-shaped screen beside the Day view. The Finances Overview was turned down for repeating the Day view.
  • Hard to see every Draft List across three weeks at once.
  • Authorising doesn't belong to a day, so it becomes a special first entry.

What moves

  • The three nav entries become one, with no tabs.
  • A new two-pane layout the app has nowhere else.
Build size

DEvery List, with a page each

Lists become records like Contracts and people: a searchable register of every List, the work queues as tabs over it, and a page for each List.

For

  • Every List gets a link that audit, invoices, Intake and notifications can point to.
  • Find any List by anaesthetist, surgeon, hospital or date, past or future.
  • The work queues are just tabs over the same register, so one table pattern serves all of them.

Against

  • A List page competes with the Day view's drawer: two places to edit a List unless the drawer goes.
  • Most of the register is Lists that need nothing.
  • No requirement asks for a List register; it's new scope.

What moves

  • A List page at its own address, with History in the rail.
  • The Review page becomes the List page's view of a submitted List.
Build size

ESplit by when

Lists holds the work before the day: Draft Lists, Conflicts, Contracts to set. Authorising moves into Finances as an Approvals tab, beside billing.

For

  • Each job sits beside its neighbours: scheduling in Lists, approvals beside billing.
  • The Lists badge counts only work before the day.
  • Finances already shows Lists awaiting approval and events awaiting the run.

Against

  • Reverses the 26 November ruling that Lists are approved in the Review queue (US-13.3.1).
  • Finances' badge counts only problems today; routine approvals would change that.
  • Finances grows to seven tabs.

What moves

  • Three nav entries become one, and the Review queue disappears into Finances.
  • Approvals uses filter pills for Lists and Events, not a second row of tabs.
Build size

Decide

My pick: A, with two borrowings

Four tabs, one per job, built on the same shell as Finances. It's the smallest change, it matches the three sections you already have, and each job keeps the columns it needs. Review's Events move to Finances › Payments, so the section is only about Lists.

From C, borrow the day group rows, so every tab reads tomorrow first. From B, borrow one rule for the badge: count each List once, and only what needs doing.
